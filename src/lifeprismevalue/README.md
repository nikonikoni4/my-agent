# 说明
该模块使用lifeprism的工具和数据，结合当前项目的myagent模块对原来lifeprism的agent提示词和工具进行评估

## 构建评估集合
构建一些业务任务，评估：
可直接统计的指标：
1）token使用量
2）工具调用次数/思考轮次turn和步骤step
3）工具调用的正确性（是否出错）
4）llm输出结果是否正确：比如需要记录某个记账，是否把数字输出对了？

比较主观的指标
1）是否是最短路径/理想路径，是否查询了本来不应该查询的工具或者反复查询同一个工具？实现一个业务应该有一个理想的最短路径.比如用户当前需要记录锻炼，正常应该是意图识别，先路由到记录agent，然后需要记录锻炼，最后询问一个是否需要同时记录时间使用情况？一共3步。
比如我需要总结一周的情况，他需要搜集某些信息，如果某些信息不明确，还需要依据behavior.md索引找到具体的日记信息进行查看等这个是比较稍微复杂且比较主观的，复杂在因为中间可能缺乏各种数据，导致情况多样性。比如按照我的要求如果出现了比较大的情绪问题，需要仔细查看其来源（通常指的是日记）

评估集合类型：
1. 路由评估，只评估路由
2. 简单问题评估：记录某些事件，1~2步
3. 中等问题评估：某些事件改变可能牵扯着别的状态改变：比如记录读书（有一个专门的自定义记录），但读书中出现的心情，读书的时间段使用情况（有一个自定义时间块记录），是否需要写进日记中？虽然这些和提示词有关系，但是默认这些都需要记录，那么agent能否遵守，或者能否都找出相关的联系并询问是否需要记录这些？找出相关的联系这个是通用的
4. 稍微复杂一点的：进行全面的总结。需要收集各种数据，还需要准备各种数据缺失的情况。

# 评估内容结合html版

上面概要里的指标方向，可以套用「结果指标 / 过程指标」这套更结构化的框架重新组织一遍：指标还是那些指标，只是按它们各自能回答的问题分层归类，方便落到埋点上。

## 一、核心框架：结果指标 vs 过程指标

- **结果指标**：只看任务最后有没有完成，回答「有没有变好」。
  - 任务成功率、答案正确率、靶场得分（在一套固定评测题目上跑出的分数）
- **过程指标**：看任务是怎么完成的，回答「为什么变好/变坏」，也就是下一步该改哪里。
  - Token 消耗、工具调用次数与顺序、重试与降级次数、耗时分布

只看结果指标，会漏掉三种变化（这三种正是概要里「比较主观的指标」想抓的东西）：

1. **结果没变，成本变了**：成功率都是 80%，但 Token 从 12000 涨到 28000、工具调用从 4.2 次涨到 9.1 次、耗时从 8 秒涨到 21 秒。
2. **结果没变，失败的方式变了**：同样 20 次失败，旧版是「没找到合适的工具」，新版是「选错了工具」，两版的修复方向完全相反。
3. **结果没变，任务变得更不稳定**：一个任务重试 5 次才成功，和一个一次就成功，在成功率上都是「成功」，但前者随时可能变成失败，重试次数上升通常是故障前兆。

## 二、过程指标分四类（对应概要里的「可直接统计」与「主观」指标）

| 类别 | 记什么 | 能发现什么问题 | 对应概要里的指标 |
| --- | --- | --- | --- |
| **预算类** | Token 消耗、耗时、工具调用次数 | 成本失控、变慢、反复重试同一个工具 | 1）token 使用量；2）工具调用次数 / 思考轮次 turn 和步骤 step |
| **路径类** | 调用了哪些工具、调用顺序 | 该调没调、顺序错了、多调了不该调的 | 「是否最短/理想路径」「是否查询了不该查的工具、反复查询同一个工具」 |
| **质量类** | 工具参数是否合法、返回结果有没有被用上 | 参数瞎填、拿到结果却忽略 | 3）工具调用的正确性（是否出错）；4）llm 输出结果是否正确（如记账数字是否对） |
| **异常类** | 重试次数、降级次数、人工介入次数 | 表面成功，但过程不稳定 | 工具调用出错后的重试 / 降级 / 人在回路 |

> **降级**：主流程走不通时，换成更简单的备用流程。比如模型调用失败，改成返回一个固定的兜底回答。
> 异常类在概要里没有单列，但值得补上：成功率会藏起「靠反复重试才勉强成功」的那部分。

## 三、意图识别

意图识别是整条执行路径的起点，它的评估归到路径类里，对应下面评估集合第 1 类的「路由评估」。

目标：
1. 精确知道用户想要做什么
2. 若不清楚用户想要什么，需要明确提问（澄清，而不是猜一个）

补充：意图识别的方法
1. 直接大模型路由
2. 关键词匹配
3. 向量匹配
4. 机器学习匹配

## 四、构建评估集合

用这套框架看，评估集合的本质是：构造一批「有理想路径」的任务，再拿 agent 的实际路径去比。概要里的四种集合类型可以这样落位：

| 集合类型 | 理想路径（人工标注） | 主要考察的指标类别 |
| --- | --- | --- |
| 1. 路由评估（只评路由） | 意图识别 → 路由到正确的 agent | 路径类（意图识别是否准确） |
| 2. 简单问题评估（1~2 步） | 例：记录锻炼 = 意图识别 → 路由到记录 agent → 记录锻炼 → 询问是否同时记录时间 | 路径类 + 预算类 |
| 3. 中等问题评估（一次事件牵动多个状态） | 例：记录读书，除自定义记录外，还要发现关联的心情、时间段，并询问是否写入日记 | 路径类 + 质量类 |
| 4. 复杂问题评估（全面总结） | 例：总结一周 = 收集信息 → 信息不明时依据 behavior.md 索引查具体日记（如情绪问题需回溯来源） | 路径类 + 质量类 + 异常类（缺数据时的降级/澄清） |

> 说明：中等问题里「找出相关联系」是通用能力，重点评的是 agent 能否发现关联并主动询问，而不是替用户决定；复杂问题的难点在于数据缺失导致的情况多样，需要专门准备数据缺失的样本。

## 五、怎么判断「路径对不对」

预算类指标只要在调用处累加计数就能拿到；难的是路径类和质量类——你怎么知道模型「应该」调用哪个工具。三种做法代价从低到高，实际系统里是叠着用的：

| 做法 | 怎么做 | 代价 | 能覆盖什么 |
| --- | --- | --- | --- |
| **规则校验** | 写死规则：参数格式对不对、工具在不在白名单（允许调用的工具清单）、关键步骤有没有执行 | 低，不需要模型 | 机械性错误，覆盖一部分 |
| **跟标准路径对比** | 人工标注一批正确路径，拿实际路径去比 | 中，要人工标注 | 标注过的那类任务 |
| **让模型判断** | 让另一个模型看完整路径，给分或者挑错 | 高，每次都要调模型 | 规则写不出来的情况 |

这正好对应评估集合里越往上越主观的那几类：简单问题用规则校验就够，中等/复杂问题需要标准路径对比，路径本身没有唯一正确答案时（如总结时该回溯哪几篇日记）才需要模型判断。

# 具体任务设计
## “记录任务”的任务架构设计

### 一、评测对象

记录类任务的评测有两个并列目标：

1. **关联规则遵守**：`custom_prompt.md` 的「关联记录规则」不是背景，而是被评产物——模型既要按规则记录，也要正确地新增 / 变更 / 不改动规则文件。
2. **记录结果与硬约束正确性**：记录集合对不对、字段值对不对、硬性规则（如同步记录约束、取值约束）有没有守住。

> 前提：本组任务只评记录，不评意图识别；默认路由到记录流程是正确的。

### 二、用例维度（三轴）

用例不按“状态”平铺枚举，而由三个正交维度组合而成，避免重叠与遗漏：

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| **规则状态** | 无规则 / 肯定规则 / 弱规则 / 否定规则 / 规则变更 | 规则来自 `custom_prompt.md`；变更再分「仅本次例外」与「永久变更」 |
| **本次输入** | 完整明确 / 模糊 / 缺必填 / 含冲突指令 / 不该触发 | 决定模型应「直接执行 / 追问 / 不触发」 |
| **复杂度** | 单记录 / 多关联记录 | 一次任务牵动的记录数量 |

- 关联规则按强度分两类：**肯定规则（强关联）**表示记录 A 时必须同时记录 B；**弱规则（弱关联）**表示记录 A 时是否记录 B 需结合本次实际情况判断。二者是独立的规则状态，不能合并。
- **不该触发**：规则存在，但本次输入（如查询、改口）让该规则本就不该生效，用于考察模型是否机械套用规则。
- **含冲突指令**：已有规则与本次指令相冲突，用于考察模型是否区分「仅本次例外」与「永久变更」。

### 三、用例覆盖要求

- 三个维度**组合生成**用例，而非逐条硬编。
- 每个考察点要**正反成对**：既要有「该触发 / 该记录 / 该追问」的正例，也要有「不该触发 / 不该记录 / 不该追问」的反例。反向样本（过度触发、过度追问）是这类任务的高频失败点，必须显式设计。
- 至少需要覆盖：
  - 每种规则状态各有用例；
  - 弱规则同时覆盖「本次满足条件 → 记录」与「本次不满足条件 → 不记录」；
  - 否定规则要能验证「后续不再追问」的持续性；
  - 规则变更要区分「仅本次例外」与「永久变更」两种期望终态。

### 四、判定机制

**期望值 = 四元组**：`任务输入 + 预置规则（提前写清楚的关联记录规则） + 期望记录（数据库）集合 + 期望规则文件终态`（多轮用例再补 `期望追问行为`）。

**判定以「落库 / 落盘 diff」为准**，模型的口头输出只作辅助——模型说「已记录」但未落库，是典型失败。

#### 数据底座与运行信息

不做统一的「前后全量 diff」，也**不逐用例复制数据**（底座约 345MB/份）。只准备**一份共用底座**，用例共用，靠时间窗归因：

```
<专用目录>/                    ← 被项目根 .gitignore 忽略
  base/                        ← 共用底座（lifeprismData 的一份复制，剔干扰后）
  summary.csv                  ← 跨用例总表
  记录任务-01/                 ← 每个大类一个目录
  │   └── case.md              ← 该大类的全部用例
  记录任务-02/
  ...
```

单次运行流程：

```
1. 用例共用 base/（需要时把 custom_prompt.md 改成该用例的预置规则）
2. 执行任务（可能多轮）
3. 从本次 session（session/*.jsonl）取 session_id 与「开始时间 / 结束时间」
4. 连同 时间 / 版本 / session_id / 测试内容摘要 / 测试结果摘要 / 是否通过 追加到 summary.csv
```

- **用例定义（`case.md`）**：每个大类目录下写清该大类的各条用例——任务输入（多轮则含各轮话术）、预置规则、裁判要点（见下）、轮次。
- **用例素材来源**：`lifeprismData/session/` 是几个月的真实使用数据，设计用例时参考真实用户话术；`show_messages.py --role user` 可按角色输出。
- **时间窗 = 本次写入的边界**：本次 session 的开始~结束时间构成时间窗，据此从库 / 文件捞出「本次任务产生的记录」，无需前后全量对比。
- **时间窗的依赖**：记录需带时间戳。多数表有 `updated_at` / `created_at` / `date`，少数只有 `created_at` + `date`，极少数无时间列（`sqlite_sequence` 可忽略）。看新增用 `created_at`，看本次改动用 `updated_at`。
- **共用底座的边界**：大多数记录类型共用互不影响；以下三处会互相影响，需单独处理——① 预算池余额是滚动值，只能断言增量（−15.3）而非绝对值；② 习惯打卡按当日幂等，同一天重复打同一习惯会失败；③ agent 会读取「最新记录 / 上次记录」，前序用例会影响其输入。必要时对这几类单独起一份快照。
- **变量控制**：同一底座，用例之间只允许 `custom_prompt.md` 不同，其余保持不变，否则无法归因。

#### 测评方式：模型裁判

**不维护统一测评脚本，也不用精确断言**。每条用例写一个小脚本，只负责**导出证据**；通过 / 失败由**裁判模型**按 `case.md` 的裁判要点判定：

1. 脚本按时间窗从库与文件取出本次写入（记录变化 + 规则文件状态 + 对话文本），session 同时作为过程指标（Token / 路径）来源；
2. 证据 + `case.md` 的裁判要点交给裁判模型，输出该用例的通过 / 失败与理由；
3. 结果摘要写回 `summary.csv`。

用模型裁判的原因：agent 记录时会压缩、改写、增删，逐字 / 逐字段的精确断言必然误判；裁判模型按「要点是否被忠实覆盖」判断更稳。

### 五、多轮约定

以下情形本质是**多轮**，用例定义必须显式给出「轮数 + 每轮用户话术 + 每轮期望行为」：

- 无规则 → 记录后询问是否建立关联 → 用户答复；
- 必填缺失 / 信息模糊 → 追问 → 用户补充；
- 多关联记录中某一项缺数据 → 先记录其余、下次再询问缺数据项；
- 规则变更 → 需用户确认「仅本次」还是「永久」。

单轮用例与多轮用例要分开标注，不能混在一起判分。
