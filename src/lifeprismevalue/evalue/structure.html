src/lifeprismevalue/evalue/ · 评估结构与进程模型

记录任务评测：结构、一次 run 的流转，以及为什么每条用例要独占一个进程

对象：src/lifeprismevalue/evalue/（runner / case / env / worker / evidence / caseload）与它调用的外部执行内核 src/evaluate/core/。第 1~3 节讲结构与流转，第 4 节讲同步与异步的边界，第 5~8 节讲进程与线程——那是这个设计里唯一"不那么显然"的部分。

先说结论，再讲推导：这份评测的并行不是靠"多开几个线程"实现的，而是一条用例独占一个进程。原因不在评测代码里，而在被测代码的写法：数据根（数据库路径、session 路径…）住在 lifeprismValue.config 的模块级全局里，而一个解释器里的一个模块只有一份——于是"同时存在两份数据根"在同一进程内在语言层面就不成立，只能靠换进程拿第二份。

1. 结构：本模块的分层与文件职责

核心是一条单向依赖：runner（装配）→ evaluate.EvalCore（调度，外部包）→ env / worker（机制与通道）→ case / evidence（领域流程，跑在子进程里）。每一层只知道自己那一层的事：调度层不认识"用例"，领域层不认识"槽位池"。

文件层它负责什么它不知道什么
caseload.py / types.py输入读 cases.yaml → 校验 → 用例对象怎么跑、跑在哪
runner.py装配 / 调度调用方建 runs/<run_id>/、组任务、调 EvalCore、把产出映射成结果、写 summary用例内部怎么跑、子进程里发生什么
env.py机制（provider）造环境（按 meta.env 从底座拼）/ 整份回滚 / 销毁 / 提供执行通道 / 开槽前自检任务内容、开几个槽位
worker.py执行通道写请求文件 → 起子进程 → 读结果文件；子进程侧的 main() 也在这里payload 的含义、结果好不好
case.py领域流程execute_case(payload, env)：切数据根 → 跑 under_test → 造证据 → 裁判 → 统计自己被谁调度、有几个兄弟任务
evidence.py领域流程给环境拍基线快照，再拿当前环境与它对比，捞"本次写入"（表按 id 比新增/改动/删除；文件比 diff）谁调用它、结论怎么用

图 1：评估结构。上半是父进程（装配 + 调度 + 机制），下半是子进程（领域流程）。红色虚线是进程边界——所有跨过去的东西都必须是可序列化的事实。

2. 一次 run 的流转

EvalRunner.run(cases_path)
  1. load_case_set(cases.yaml) → meta + meta.env + cases[]
  2. _prepare_run：核一遍 meta.env（路径 / 库 / keep_tables 都在？）；建 runs/<run_id>/{envs, ipc, logs, sessions}；写 run.json
  3. 组任务：用例 i → WorkerTask(entrypoint, payload={cases_path, index, case_dir, baseline_dir,
                                              session_folder, turn_timeout, scan_other_changed_files})
  4. EvalCore.run(tasks)：开 max_workers 个槽位 → 逐条派发 → 复用前 reset_env → 收尾回收
  5. 产出按入参同序映射成 CaseResult → 写 runs/<run_id>/summary.csv，并追加 runs/summary.csv

槽位就是"一份环境 + 一条通道"的配对，任务数通常远大于槽位数。真正干活的是子进程；父进程里的线程只负责"等"。

图 2：同一个 run 里的两层。父进程线程被 subprocess.run() 阻塞，子进程在跑；并行度等于槽位数，等于同时存在的子进程数。

为什么 runner 里还有一个 asyncio.to_thread：它不贡献并行度。整条执行路径（EvalCore + subprocess.run）都是同步阻塞的，包一层只是为了避免堵住调用方的事件循环——一次 run 期间它只占 1 条线程，而那条线程自己也只是在等。脚本/CLI 直接用的话，去掉它没有区别。

3. 跨进程传了什么：请求 / 结果 / 日志

跨过进程边界只能传"事实"（字符串、JSON、路径），不能传对象。所以父进程把"这一条任务的输入"写成请求文件，子进程照它把上下文重建出来：

python -m lifeprismevalue.evalue.worker <请求.json> <结果.json>

请求.json = {
  "entrypoint": "lifeprismevalue.evalue.case:execute_case",   // 要调哪个函数（字符串）
  "payload": {                                                // 领域层载荷，core 不解释
    "cases_path": "…/cases.yaml", "index": 3,                 // 第 index 条用例
    "case_dir": "…/003_1.2-a", "baseline_dir": "…/003_1.2-a/baseline",
    "session_folder": "…/runs/<run_id>/sessions",
    "turn_timeout": 300.0, "scan_other_changed_files": true
  },
  "env": { "root": "…/envs/env01", "key": "env01", "template": "…/base" }   // core 只认这三样：复制清单与库配方留在机制层
}

结果.json = {"ok": true, "output": {…}}          // 成功：output 就是 execute_case 的返回
          | {"ok": false, "error": "类型: 消息"}  // 子进程内部崩了
字段子进程拿它做什么
entrypointWorkerTask.load_entrypoint() 解析成可调用对象——解析发生在子进程里，因为函数对象没法跨进程搬
payload原样交给 execute_case(payload, env)；用例本体不在里面（只给"第几条"），子进程自己去读 cases.yaml，免得两份数据不一致
env重建 LifeprismEnv(root, key, template)；root 是 config.use_data_path() 的目标，key 进日志，template 保持句柄语义完整
通道落点生命周期
请求 / 结果ipc/<token>.request.json、.result.json成功即删（痕迹已在用例目录与日志里）；失败留着当证据，可手工重放
子进程日志logs/<用例目录名>.log（stdout 与 stderr 合并）一直留着。子进程里的异常栈、agent 日志都在这；失败时错误信息会附带日志尾部
环境变量继承父进程 + PYTHONPATH 透传 sys.path子进程要能 import lifeprismevalue / myagent / evaluate；API key 等依赖也走这里

4. 同步与异步的边界：为什么 asyncio.run 只出现在一个地方

调度内核的 Worker 契约是同步的——core.py 里那一行 output = slot.worker.run(task) 就是一次普通函数调用，没有 await；Worker.run 的抽象签名也是同步的。但被测对象是异步的：ReActAgentLoop.send() 只把消息入队，turn 在后台 asyncio 任务里跑，要知道"本轮跑完了"必须 await 一个事件、还得配超时（TurnCollector.wait_turn → asyncio.wait_for）。

于是出现一个"同步主干里夹着一段异步"的问题，两种处理方式：

方案代价
(a) 整条链改成 async：core 的派发、worker、provider 全变协程异步会"传染"到调度层：队列租借与线程池语义要重写成 asyncio 版本；每个槽位要自己管事件循环；而子进程边界天生是同步的（subprocess.run + 全新解释器的顶层调用），最外层还是要落回同步——等于上下两头都在做转换
(b) 把异步收成一座"岛"（本项目）：主干保持同步，只在最内层开一个事件循环只在一处出现 async：CaseExecutor.run()（同步）内部一句 asyncio.run(self._run_async(ctx))；进出岛都是同步——进去一句调用，出来一个 dict
为什么岛要放在领域层最里面那一层：因为它必须和"唯一需要 await 的东西"待在一起。只有 case.py 知道"要等 turn/end"；core 不知道、worker 不知道、env 更不知道。异步如果往外挪一层，那些原本不需要知道"协程"的模块就得被迫懂它——把变化点收在不认识它的那些层之外，这正是第 1 节那张分层图的同一条纪律。

图 3：全链路的同步 / 异步分布。同步主干一条线走到底，异步只在最内层成岛；asyncio.run 是唯一的进出口。

4.1 这个结构带来的三条注意点

① asyncio.run 不能在"已有事件循环在跑的线程"里调用（会直接 RuntimeError: asyncio.run() cannot be called from a running event loop）。当前两处调用环境都是安全的：真跑时它发生在子进程里——全新解释器、顶层同步调用，没有循环；测试里 CaseExecutor().run(ctx) 也是同步上下文里调的。反过来说，谁要是哪天想在 async 的函数里直接调 CaseExecutor.run()，就会当场炸——好在父进程从不执行用例本体（见第 5 节的进程边界），天然绕开了这件事。
② asyncio.run 退出时会关掉事件循环并取消残留的后台任务，而 agent 的后台循环与 session 的定时落盘（每 2 秒一批）都在其中。所以 case.py 在 finally 里固定两件事、且顺序不能换：先 persist_session_now() 把缓冲区刷下去，再 cancel() 停掉循环——顺序颠倒了，最后一批记录就随循环一起没了。
③ 和循环绑定的对象必须在同一个循环里创建与等待。TurnCollector 里的 asyncio.Event 是在 _run_async 内部构造的，也就是在 asyncio.run 建的那个循环里——所以"创建"和"等待"必然同源。这类对象若在岛外创建、岛内 await，等的是一个永远没人 set 的事件（症状：卡到超时，而且看不出错在哪）。

5. 为什么必须换进程：被测代码把数据根放在全局里

这不是 evaluate 的要求（它的示例 worker 就是进程内直接调 callback 的），而是被测代码的写法带来的硬约束。链路是这样：

tools/*.py  ──►  data/*.py  ──►  db.connect()  ──►  config.get_db_path()  ──►  config._db_path
   （工具层一个 config / db 都不 import）               每次建连接都现读这个模块级全局
用什么路径从哪来
数据库（记录类工具）db.connect() → config.get_db_path()
session / chat_historydata/session.py 直接用 config.get_session_path() / config.CHAT_HISTORY_PATH
提示词、agent 工厂config.get_lifeprism_data_path()
文件类工具（读日记、写 md）不经过 config：路径是模型给的参数（提示词里把工作目录写给它了）
两个关键细节：
① get_db_path() 是"每次调用现读"，不是 import 时绑定的常量——所以 use_data_path() 改了全局之后，新建立的连接立刻用新库。整个切根机制能成立，全依赖于这一点。
② config 是一个模块，而模块在一个解释器里只有一份（sys.modules 缓存）——所以"同时持有两份数据根"在同一进程里，在语言层面就不成立，不是代码写得不够好。

6. 线程的内存模型：你到底能"隔离"什么

这是理解整件事的知识底座。图 4 是两种隔离单位的对照：线程共享堆、只有栈是自己的；进程两套地址空间，互不可见。

图 4：线程 vs 进程的内存视图。左侧红框是那个"只有一份"的全局——它就是约束的全部来源。

6.1 竞态：两行相邻代码之间会被切走

共享一份可变状态 + 至少一个线程在写 → 结果取决于"谁先谁后"，而那个先后由调度器决定，不可控、不可复现。这就是竞态。

图 5：竞态时序与"锁 vs 复制"。左框说明为什么加锁会退回串行，右框说明换进程为什么能同时拿到 N 份。

6.2 能在同一进程里装下 N 份值的三种做法（都必须改被测代码）

做法值住在哪同一进程能并存 N 份吗要改被测代码吗
加锁（互斥）还是那个全局不能——只是排队，同一时刻仍只有一份不用（因为根本解决不了）
参数化：save(text, db_path)各线程自己的栈帧能要：db.connect() 得收参数
threading.local()每线程一份能（线程维度）要：读的地方改成读 local
contextvars.ContextVar每个上下文一份（线程 / asyncio 任务各自继承）能（上下文维度，现代推荐）要：同上
换进程（本项目）每个进程一份模块对象能，且不需要改动测代码不用——改换地址空间
评测的权限边界：评测要测的是"被测代码在真实写法下的表现"，所以不该为了跑得快去改被测代码（改成参数化就不在测原来那份东西了）。这就是本题里第 5 行被选中的原因：它是唯一"不改被测代码"还能拿到 N 份隔离状态的手段。

7. 知识卡：这条设计链上容易被卡住的点

问题一句话答案
线程之间的内存隔离是什么样的？没有隔离：共享整个堆（模块对象、全局、类属性、单例都只有一份），各自只有栈 / 寄存器 / thread-local / contextvar 值
GIL 能保证什么？只保证"同一时刻只有一个线程在跑字节码"，不保证一段多步操作不被打断——所以它挡不住竞态
什么叫竞态？结果取决于执行先后，而先后由调度器定 → 随机、不可复现。条件是：两个执行者 + 同一份可变状态 + 至少一个在写
多线程下每个 worker 都改全局路径，会怎样？互相覆盖，数据写错环境，且不报错（写入本身成功，只是落在别处）
加锁能解决吗？不能。"一个变量同时等于两个值"锁做不到；加锁后临界区只能取"一整个用例"，等于退回串行
为什么模块级全局只有一份？模块在进程内只被 import 一次（sys.modules 缓存），所有线程拿到的是同一个模块对象
那"每个 worker 一个独立环境"怎么实现？让"一份环境"对应"一个进程"：各子进程重新 import，各有一份 config，切根互不影响
子进程是什么时候起的、起几条？EvalCore 开槽时给每条槽位造一条通道；跑任务时 worker.run() 里 subprocess.run()。同时最多 max_workers 条
命令行 python -m …worker 最终执行的是哪个函数？本模块的 main()（__main__ 守卫触发）→ 它会解析 entrypoint 并调用 case.execute_case()
IPC 是什么、为什么用文件？进程间通信。共享内存传不了对象，stdout 被日志占用，argv 塞不下嵌套 JSON；文件还能在失败时留作证据
请求里为什么就这三样？够子进程"从零重建"就行：要调的函数名、要跑第几条（不是用例本体）、以及重建 Env 句柄的三要素
线程数 = 并行度吗？不是。线程只负责"等"，并行度 = 槽位数 = 同时存在的子进程数
为什么不让整条链都变 async？异步会传染到调度层与子进程边界；收成"岛"就只在一处出现——CaseExecutor.run() 里的一句 asyncio.run，进出岛都是同步
asyncio.run 为什么放在最内层？只有 case.py 需要 await（等 turn/end）；放外层会让 core / worker / env 这些不需要它的模块被迫懂协程
asyncio.run 有什么坑？不能在已有循环运行的线程里调；退出时会取消残留任务（所以必须先 flush 再 cancel）；asyncio.Event 这类对象要在同一个循环里建与等

8. 两条推论（用来检验有没有理解）

推论一：约束消失，子进程就该消失。 如果哪天被测侧把数据根改成显式参数或 ContextVar，不再依赖模块全局，那么进程内线程 worker 就能同时跑 N 份数据根——那时只需要换掉 provider.create_worker 一处（worker.py 整条跨进程通道都可以删掉），EvalCore、runner、case.py、evidence.py 一行都不用改。这也是 evaluate 把"造通道"归给 provider、把 entrypoint 设计成字符串的原因：执行方式是被测系统的属性，不是调度内核的属性。
推论二：代价记在谁的账上很清楚。 每用例一次进程启动（外加一份环境），本质都是在为"被测代码把数据根放在进程级全局里"买单。其中环境那部分的账已经用「按配置拼」压下去了——只拼本次要用的东西（底座整份 122MB → 环境 ~1.6MB），剩下的主要是进程开销。要接着降本，方向同样是让被测侧的状态可传入（参数化 / contextvar），而不是在评测侧抠进程开销。
