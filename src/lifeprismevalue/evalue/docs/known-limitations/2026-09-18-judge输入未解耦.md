# judge 输入未解耦

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿 |

**状态**：acknowledged

## 问题描述

judge 的**判断标准**是解耦的：写在用例的 `rubric` 与角色提示词里，改它不用动代码。
但**喂什么材料**不是——`_build_judge_input` 写死了三样：

```
判分要点（case.rubric） + 本次证据（evidence） + 对话记录（transcript）
```

推论：想加一类判据，只要它需要这三样之外的材料，就必须改代码。最直接的一例是
**过程评分**（拿工具调用的次数 / 顺序 / 参数是否合理来判分）：

- `stats.json` 的 `PathStats` 已经**精确**算好了：`tool_call_count`、带完整 `arguments`
  的 `tool_sequence`、`error_call_count`、`consecutive_repeats`、`tool_counter`；
- 但 `stats.json` 与 `judge.json` 是**并列的两个产物**，没有任何一步把 stats 递给裁判；
- 裁判实际看到的对话里，工具痕迹只有 `[tool_result:工具名]`——`_read_transcript` 处理了
  `user/message`、`assistant/message`、`tool/result`，**唯独漏掉 `tool/call`**
  （才记着工具名与完整参数的那条）。

由此分成两档后果：

1. **能数，但不能判**：一次成功的调用恰好留一条 `tool_result`，所以裁判**能数出次数**；
   但只要有一次调用没留下结果（中断、崩溃、工具抛异常），它就会少数一次，**而且不报错**。
2. **完全看不见**：参数对不对、顺序合不合理、该调没调、有没有反复调同一个工具——都判不了。

> 实测 S-1：裁判给出「工具调用次数为 5 次」，`stats.json` 的真实值也是 5——**这次是对的**。
> 但对的原因是「调用与结果恰好一一对应」，是巧合，不是设计保证。

## 影响范围 + 严重程度

- **影响范围**：所有想判「过程」的用例，即路径类 / 预算类 / 异常类指标。
- **严重程度**：中。不影响已有用例的结论（它们判的是落库 / 落盘结果），
  但它**限制了评测能问的问题**——`src/lifeprismevalue/README.md` 里设计好的
  「过程指标」一整套（工具调用次数与顺序、是否最短路径、重试与降级），目前落不了地。

## 当前假设（系统依赖的脆弱前提）

**裁判能看到的工具信息，恰好够数次数。**

这个前提没有保证：它依赖「每次调用都产出一条结果」。中断、崩溃、工具异常时都不成立，
而那时恰恰是最该被判出来的时候——一个「反复调用失败」的用例，在裁判眼里可能只是
「调用次数很少」。

## 触发条件

用 `rubric` 要求裁判判任何涉及工具**过程**的内容时即触发，包括但不限于：

- 「工具调用次数 ≤ N」
- 「是否按理想顺序调用」
- 「是否反复调用了同一个工具」
- 「是否调用了不该调用的工具」

## 临时方案或计划改进

**方案未定**（本次只记录，未讨论）。

已知的难点在**输入侧的声明方式**：即便把 `stats.json` 接上，只要「stats 里写什么」
仍由统计组件的代码决定，改一次 stats 就要连带改多处，耦合并没有真正解开。
真正要解的是「**用什么材料**由谁说了算」——是代码写死，还是用例声明。
