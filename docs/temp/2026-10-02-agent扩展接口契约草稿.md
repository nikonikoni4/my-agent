# Agent 扩展接口契约草稿

日期：2026-10-02。状态：讨论稿。

本稿承接 [内核与外部策略解耦初稿](2026-10-02-agent内核与外部策略解耦初稿.md)。固定控制决策、内核执行、外部解释业务错误是已确认方向；以下具体签名、字段和默认行为都是待确认提案，不代表实现已变更。

## 1. 契约编写原则

每个接口明确：调用时机、输入及其归属、返回值、失败行为、取消行为、允许的副作用和生命周期。Protocol 描述可调用能力，数据类型表达输入输出，运行时校验保护控制边界。

先定义语义和必要信息，再确定 Python 类名、模块位置及迁移方式。不同扩展点不强行共享万能策略接口。

## 2. 接口清单

| 接口 | 调用方 → 实现方 | 接收 | 返回 | 核心问题 |
| --- | --- | --- | --- | --- |
| 模型调用 | loop → 外部模型调用器 | 消息快照、工具定义、调用上下文 | 流片段及完整结果 | 请求参数、流结束、部分输出和取消 |
| 错误决策 | loop/事件分发 → 外部处理器 | 原始异常及执行现场、下游委托函数 | 固定错误决策或无人认领 | 认领顺序、重试范围、预算、终止语义 |
| 工具执行前裁决 | loop/事件分发 → 外部处理器 | 整批工具调用及只读现场、下游委托函数 | 固定工具裁决 | 整批或逐条认领、缺项、拒绝与合并 |
| 工具执行 | loop → 工具执行层 | 工具调用与执行上下文 | 工具结果 | 返回失败结果和抛异常的分界 |
| 观测通知 | 框架 → 订阅方 | 事实记录或事件快照 | None | 不参与循环控制、订阅方失败隔离 |
| 注册与生命周期 | 使用方 → 装配层 | 事件契约、处理器/组件 | 注册结果 | 顺序、重复注册、持有引用、关闭责任 |

优先确定错误决策和模型调用契约，再细化工具裁决；不在本稿中重做 Session、持久化和提示词全部接口。

## 3. 错误决策输入（提案）

### 3.1 ErrorContext

| 信息 | 建议类型/语义 | 理由 |
| --- | --- | --- |
| error | Exception，原始异常实例 | 外部处理器按自己的类型识别，不要求框架异常父类 |
| agent_id、turn_id、step_id | 框架关联标识，具体类型待定 | 定位失败现场与日志关联 |
| operation_id | 本次失败操作的关联标识 | 区分同一步里的模型调用或具体工具执行 |
| phase | 框架定义的阶段枚举 | 标明错误发生位置，不推断业务根因 |
| retry_count | 本恢复范围已实际执行的重试次数；首次为 0 | 策略需要理解计数，计数事实仍由内核维护 |
| remaining_retry_budget | 当前配置下剩余重试额度 | 外部表达意图，不能绕过内核预算 |
| progress | 只读执行进度快照，字段待细化 | 标明是否有部分输出、哪些工具已开始/完成，防止不安全重放 |

输入是只读现场，不传可直接改写的 loop、AgentContext 或活动 Session。需要更多历史信息时，另行定义最小只读查询接口或由装配时注入外部依赖，避免为了方便暴露整个运行态。

Exception 实例只用于进程内决策，不直接 JSON 序列化。持久化记录异常类型、消息、因果链和关联标识；结构化异常元数据是否增加，后续按观测需求决定。

CancelledError 独立传播，不作为普通错误策略输入。框架自身编程错误不能因一层宽泛捕获而被伪装成 provider 错误；捕获范围按执行边界定义。

### 3.2 处理器签名

保留当前 async waterfall 委托方式的提案：

```python
NextErrorHandler = Callable[[], Awaitable[ErrorDecision | None]]

class ErrorHandler(Protocol):
    async def __call__(
        self,
        context: ErrorContext,
        next_handler: NextErrorHandler,
    ) -> ErrorDecision | None: ...
```

以上为签名示意，不是可直接导入的实现。

- 认领：直接返回合法 ErrorDecision，不执行下游。
- 不认领：`return await next_handler()`。
- 下游全部不认领：返回 None，由内核执行明确兜底。
- None 只表达无人认领；策略异常和非法决策分别报告，不转换为 None。
- 提议每个处理器最多委托一次；具体如何约束需实现设计。
- 外部业务恢复可以等待网络或人工应答，但必须响应取消，不能自行重跑 loop 或修改其私有状态。
- 认领顺序先沿用显式注册顺序；是否增加 priority 待定。

## 4. 错误决策输出（提案）

建议使用封闭的联合类型，而不是一个带大量可选字段的通用 dict：

```python
ErrorDecision = Retry | Continue | Terminate
```

| 变体 | 参数提案 | 内核执行语义 | 约束 |
| --- | --- | --- | --- |
| Retry | delay_seconds: float | 对契约规定的恢复点重试 | 延迟有限且非负；计数及预算由内核校验 |
| Continue | grant_steps: int = 0 | 从规定的位置继续；可申请额外步数 | 非负整数；仅允许在可继续的状态使用 |
| Terminate | outcome: failed/interrupted/completed，具体值待定 | 结束当前 turn，并按指定语义记录 | turn 终止与后台 loop 退出的关系需单独明确 |

delay_seconds 是解耦优先的提案：指数退避、jitter、供应商 Retry-After 等由外部策略计算，内核只负责可取消等待和预算校验。它与现有内核持有退避公式的设计不同，需要确认后才能替换。

“立即重试”和“退避重试”可合并为 Retry，区别只在 delay_seconds。此合并尚未确认。

Retry 的具体恢复点是本接口落地的前置决策：重试模型调用、失败工具还是整个 step，不能靠一个名称含糊表达。初步建议优先约束为模型调用恢复；工具重放另设明确契约。即使动作类型合法，执行现场不支持该动作时也必须拒绝。

Continue 也必须指定继续位置，不能因发生任意错误就自动开启下一 step。工具消息配对和部分结果收尾应由内核先保证。

切换模型、更新外部调用配置、等待人工或压缩上下文，不自动扩张为 loop 动作。它们可以由外部组件执行，再返回合法决策；若涉及修改框架拥有的数据，必须通过另行定义的公开能力接口实现。

终止范围、终态值及是否上抛原异常尚未确定，不把当前 as_error 的后台退出副作用直接固化为新契约。

## 5. 模型调用契约（待逐项讨论）

建议先只要求 loop 实际消费的流式能力，非流式 chat 是否必要另行确定。

输入应区分：消息与工具定义是本次请求的快照；模型名、采样参数、路由和鉴权由谁持有需要明确。不能要求 loop 理解供应商私有配置，也不能丢失 request trace 所需的可观测配置。

返回形式需要选择并严格规定：

- 保留现有 AsyncIterator[StreamChunk | LLMResponse] 时，完整结果必须恰好一次且是最后一项；正常耗尽却未产生结果应视为契约违例。
- 若使用独立终结事件，则其完整结果、usage 和 finish_reason 的归属也必须统一。
- 中途异常表示本次调用失败，已发出的片段不可撤回；原始异常进入错误决策事件。
- 调用器负责释放自己创建的流资源，框架不得关闭使用方共享的长期客户端。
- 外部内部重试如不可观测，需明确框架的“一次调用”口径。

消息、工具 schema、结果和工具参数的具体字段在下一轮讨论中对照现有数据类型确定，本稿暂不新增一个宽泛 kwargs/Any 接口。

## 6. 工具裁决与观测通知（待细化）

工具执行前裁决输入保留整批视野，返回专用 ToolDecision，不能复用 ErrorDecision。需确定：逐条允许/拒绝、批内缺项默认行为、多处理器如何组合、是否允许替换调用，以及无人认领是否放行。

观测通知接收事实快照、返回 None，不通过返回值控制执行。同步 emit 与异步 waterfall 保持语义区分；观测订阅失败是否隔离以及如何留痕需明确。

## 7. 当前实现需要对齐的地方

- RequestErrorPayLoad 目前只有 error_type，实际装的是异常实例，缺少明确执行现场。
- 错误决策目前是无类型 dict，字段组合和未知 decision 未形成固定类型约束。
- EventService.waterfall 当前把回调异常转为 None，混淆策略失败与无人认领。
- TOOL_CALL 在 EventSpec 中声明 emit，loop 中实际 await waterfall；契约语义需要统一。
- 工具裁决目前传入活动 Session，需讨论只读能力边界。
- 模型流失败补齐依赖 LLMCallError，需要支持外部异常且保证捕获边界准确。
