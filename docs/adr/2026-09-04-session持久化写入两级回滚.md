# Session 持久化写入的两级回滚决策

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿 |

## 问题界定

### 问题简述

session 的持久化组件把事件记录以 JSONL 逐批追加到文件。追加写入过程中随时可能失败（磁盘满、文件被锁、权限变化），而 session 日志不允许出现"写了一半"的状态——一旦文件里留下半批数据，加载和排查都无法判断哪些记录是完整的。必须决策：用什么机制保证写入的正确性。

### 讨论范围

- 模块：`src/myagent/agent/core/session/persistence.py` 的 `presist()` 写入路径及其失败处理。
- 需要回答的关键问题：`with` 上下文管理器不提供原子性时，如何保证"整批要么都在文件里，要么文件保持原样"；回滚操作自身失败时如何兜底。

### 非讨论范围

- 进程崩溃（内存状态丢失）后的残缺尾巴修复——用户明确列为已知限制，不在本 ADR 考虑，将来实现加载逻辑时独立决策。
- 换用数据库等不同持久化后端——接口已抽象，后端更换不属于本决策。
- 多进程/多写者并发——已确认排除（见决策前提 4）。

### 模糊信息的明确定义

- `session 不能写入出错`：本文中具体指"文件不允许出现半批状态，文件状态必须永远可推断"，不指"任何情况下最后一批都不许丢"（后者属于断电级持久化，用户确认不纳入当前范围）。

### 问题深度

属于可靠性工程的基础机制问题：写入失败恢复策略决定了文件的读取端契约、测试方式和后续扩展空间，是持久化层的长期约束。

## 现状

- 持久化组件按"200ms 或攒批"的设计把 buffer 整批写入 JSONL 文件，写入失败时 buffer 保留、等下一轮重试。
- Python 的 `with open(...)` 只负责退出时关闭文件，不保证写入原子性；即使把整批合成一次 `write()`，磁盘满时也可能只落一半字节。
- 失败后如果直接重写整批，会在残缺数据上追加，产生重复行；文件状态从此无法推断。
- 同类问题在业界有正式名字（torn write，撕裂写入）和成熟解法，SQLite 回滚日志与 deepseek-harness 的 JSONL 后端是两个可参照实现。

## 决策前提

- 前提 1（事实，已验证）：`with` 上下文管理器不保证写入原子性，只负责退出时关闭文件；单次 `write()` 在磁盘满等场景下也可能只写一半。
- 前提 2（用户约束）：session 日志不允许出现半批状态，文件状态必须永远可推断——"整批要么都在，要么都不在"。
- 前提 3（用户确认）：失败边界为"不允许半批状态即可"；最后一批在断电/进程崩溃时允许丢失；fsync 不纳入当前范围。
- 前提 4（用户确认）：单写者——persistence 的 loop 是唯一写该文件的代码，多进程/多写者不在考虑范围。
- 前提 5（讨论确立）：`OSError` 是环境错误，必须恢复而非崩溃；序列化 `TypeError` 是代码 bug，必须暴露而非吞掉。
- 前提 6（事实，经检索核实）：该问题业界有标准解法；SQLite 回滚日志"记录数据库初始大小，回滚时截断回去"与本决策同型。

## 可选方案

### 方案 A：整批一次写入，失败直接重写整批

失败后不做恢复，重试时把整批再写一遍。

**优势**

- 实现最简单，没有额外状态。

**劣势**

- 写一半失败时文件留残缺字节，重写后出现重复行，文件状态不可推断。
- 违反前提 2。

### 方案 B：临时文件 + rename 原子替换

每次写入把全量内容写到临时文件，再用原子 rename 替换。

**优势**

- POSIX 层面的原子性，崩溃后临时文件可丢弃。

**劣势**

- 日志是只追加、持续增长的，每次写全量重写的代价随文件体积线性增长，不可接受。

### 方案 C：tenacity 装饰器自动重试

用现成重试库包装写入函数。

**优势**

- 开箱即用，重试策略可配置。

**劣势**

- 重试不等于原子，不解决半批状态问题；新增依赖；同步重试会阻塞事件循环。

### 方案 D：两级回滚（记录写前大小 + 失败截断 + 下次写入前补截断）

写入前记录文件字节数 `before`，整批一次写入；失败时记住 `before` 并尽力当场截断回原大小；当场截不动（如文件被占用）则保留记录，下一次写入的第一步先补截断，补截断没完成就直接中止，绝不往残缺文件上追加。

**优势**

- 文件状态永远可推断：要么含整批，要么保持原样，要么处于"待补截断"的已知中间态。
- 代价恒定：记录一个整数，失败时只截掉残缺部分。
- 覆盖了"回滚自身也失败"的极端情况。

**劣势**

- 引入 `_pending_truncate` 内存状态，进程崩溃时丢失（记为已知限制）。
- 截断没有 fsync，断电窗口理论上仍可能留残缺（记为已知限制）。

| 前提条件 | 对应方案 | 备注 |
|----------|----------|------|
| 前提 1 + 2 + 4 成立（with 非原子、不许半批、单写者） | 方案 D | 当前选择 |
| 前提 3 收紧为"断电也不许丢最后一批" | 需要独立决策：fsync 与显式 flush 接口 | 不在本 ADR 范围 |
| 前提 4 失效（出现多写者） | 需要独立决策：文件锁或直接换后端 | 方案 D 的两级回滚依赖单写者，不可沿用 |

## 演进历史

| 版本 | 方案 | 解决的问题 | 引入的新问题 |
| ---- | ---- | ---------- | ------------ |
| v1 | 失败时当场截断回滚（尽力而为） | 半批数据不再出现 | 用户质疑：回滚用的 open 也可能打不开；一旦回滚失败，下次写入前的 stat 会把残缺文件固化成新基线 |
| v2 | 用户提出：记住 before，下次写入先截断再写 | 消除基线固化漏洞 | 单纯推迟回滚会放弃"当场就能恢复"的常见场景（磁盘满时截断必成功） |
| v3 | 两级回滚：先记回滚目标再尽力当场截断；下次写入第一步补截断，补不上绝不写新数据 | v1 与 v2 的问题同时解决 | — |

## 最终决策

当前成立的前提：前提 1、2、3、4、5、6 全部成立。

因此选择 `方案 D：两级回滚`。

前提失效时的切换路径：见"决策逻辑"表——前提 3 收紧时独立决策 fsync 方案；前提 4 失效时独立决策文件锁或后端更换；崩溃级恢复维持已知限制，待实现加载逻辑时独立决策。

## 决策原因

- 原子性只能靠失败后的补救动作建立，不能靠写入动作本身——这是 `with`/`write` 都不提供的保证，SQLite 用同样机制（记录初始大小 + 截断回滚）在生产环境验证了该路线。
- 追加日志场景下方案 D 代价恒定，方案 B 的全量重写代价随文件增长不可接受。
- 两级结构把"回滚自身失败"从漏洞变成显式处理路径，且失败路径有 8 个测试锁定（含"文件被长期占用"的极端场景），行为不会回归。
- 方案 v2 → v3 的修正由用户提出，保证了"记住回滚目标"这一关键状态没有遗漏。
