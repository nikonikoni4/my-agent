# 决策：槽位机制采用统一注册表与两种分发语义

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿（概念层决策） |
| 2.0 | 按 write-decisions 决策文档模板重写，补齐骨架节 |

## 问题界定

### 问题简述

agent 运行过程中需要挂载大量横切关注点：思考内容与工具步骤的对外呈现、执行轨迹记录、工具执行前的权限判定与人工审批，以及未来可预见的脱敏、超时、指标等。这些关注点需要一个统一的挂载机制，且该机制的形状将决定 core 层契约的形状。在开始 core 编码前必须确定它，否则后续每个关注点都会各自发明挂载方式。

### 讨论范围

- agent 运行管线（turn 开始 → LLM 调用 → 工具调用 → turn 结束）上横切关注点的挂载机制。
- 本决策需要回答的关键问题：挂载机制采用什么形态？新增关注点时以什么方式介入？

### 非讨论范围

- 链顺序的治理方式（文档约定 vs 注册优先级选项）——未决策。
- 槽位首版覆盖范围（仅工具链，还是同时预留 LLM 调用、系统提示组装的链）——未决策。
- 是否引入 DHS 其余分发语义（parallel / serial / bail）——未决策。
- 观察事件名的封闭性约束方式——未决策。
- 崩溃恢复是否引入及其阶段——未决策。
- 具体代码与类型设计——本决策停留在概念层。

### 模糊信息的明确定义

- `槽位（slot）`：agent 运行管线上的固定节点，外部行为通过注册挂载其上，节点本身不因扩展而修改。
- `关注点`：权限、审批、可观测、脱敏、超时、指标等横切需求，一个关注点对应一个挂载单元。
- `分发语义`：注册表调用已注册回调的方式。本决策只涉及两种：emit（扇出）、waterfall（链式）。

### 问题深度

架构原则层。该机制是 core 层与所有上层之间的契约形状，决定未来所有横切关注点的接入成本，难以在编码后逆转。

## 现状

- 项目处于目录骨架阶段，core 文件为空，尚无实现约束。
- core 硬约束：仅依赖 Python 标准库与 typing；实现层不得反向依赖。
- 用户的原始需求是"固定槽位上可添加记录内容，也可添加作为 hook，以支撑审批、记录、权限、沙箱、可观测等"——术语初始模糊，经需求澄清对齐为 [CONTEXT.md](../../CONTEXT.md) 的词汇。
- 对照系统 DHS（deepseek-harness，用户指定参照）：其权限、超时、脱敏、指标、审批、spill 等关注点全部通过 cordis 事件系统（一个注册表 + 多种分发模式）注册挂载，管线代码保持稳定。经源码核实：cordis 内部即回调注册表（`_hooks` 字典），"事件总线"是它扮演的角色。
- 已知 DHS 弊端（源码分析）：emit 不兜订阅者异常；注册顺序（prepend）成为隐式全局状态；框架重量级（fiber effect 等响应式机制在 Python 中无对应物）。

## 决策前提

- 前提 1（事实，源码核实）：DHS 的全部横切关注点均通过注册挂载，无一通过修改管线实现。新增关注点不改管线源码是其可扩展性的实际形态。
- 前提 2（用户明确表达）：核心价值是"注册机制——无论新增什么内容，都通过注册来扩展，不一定需要修改源码"。
- 前提 3（需求对齐结论）：观察类需求（前端呈现、轨迹记录）与拦截类需求（权限、审批）的失败哲学相反：观察要求订阅者故障不外溢，拦截要求无人应答即拒绝（fail-closed）。两者不能共用一种分发语义。
- 前提 4（用户明确表达）：本决策停留在概念层，不涉及具体代码与类型设计。
- 前提 5（事实）：管线节点是固定且封闭的集合，需要开放的是节点上可挂载的内容。

## 可选方案

### 方案 A：按关注点枚举 Protocol 接口

为每类关注点定义独立的抽象接口（权限门接口、审批接口等），上层实现并注入。

**优势**

- 接口签名即契约，"问什么、答什么"完全显式，类型检查可拦截误用。
- 测试可直接注入 mock，无需注册表间接层。

**劣势**

- 关注点是开放集合：每个新关注点（脱敏、超时、spill、指标）都要新增接口定义，即修改 core 源码——违背前提 2。
- 教学原型验证中被用户质疑"扩展性不强"，实际无法覆盖 DHS 中"设计时想不到"的关注点（如 system-prompt 组装拦截、telemetry 脱敏）。

### 方案 B：统一注册表 + 两种分发语义（emit / waterfall）

一个回调注册表；观察槽用 emit（扇出，只出不进），拦截槽用 waterfall（链式，中间件拿 next() 可放行/否决/环绕）。扩展 = 注册，不改管线。

**优势**

- 直接满足前提 2：新关注点 = 注册新回调/新环节，管线与槽位零修改。
- 两种分发语义对应前提 3 的两种失败哲学，各自在分发层实现"异常包含"与"fail-closed"。
- 与 DHS 结构同构，可复用其验证过的场景清单（8 类拦截场景均为注册形态）。

**劣势**

- 契约显式性下降：签名不再逐关注点声明语义，"此处做权限判定"转移到约定与文档（可由事件名封闭等手段缓解，属后续设计）。
- 链顺序成为需要治理的显式装配内容（DHS 的 prepend 弊端即源于此）。

### 方案 C：消息队列 / 独立消费任务

事件推入队列，独立任务消费。

**优势**

- 天然背压，慢消费者（如落盘）不占主循环时间。

**劣势**

- 只适合观察出口，无法表达拦截所需的"发问—等待终态回答"语义。
- 崩溃时内存队列丢失。

## 决策逻辑

| 前提条件 | 对应方案 | 备注 |
|----------|----------|------|
| 前提 1、2、5 成立（注册不改源码是硬需求，关注点开放） | 方案 B | 当前选择 |
| 前提 2 失效（关注点收敛为封闭小集合，类型安全收益高于扩展性收益） | 方案 A | 备选触发条件 |
| 仅观察出口、无回流需求 | 方案 C | 不满足前提 3，仅可作为未来单个订阅者的内部实现 |

## 最终决策

当前成立的前提：前提 1-5 全部成立。

因此选择 `方案 B：统一注册表 + 两种分发语义（emit 扇出 / waterfall 链式）`。

前提失效时的切换路径：若未来关注点集合收敛为封闭小集合（如本项目转型为固定流程引擎），类型安全的收益将超过扩展性收益，切换到方案 A（按关注点枚举 Protocol 接口）。

## 决策原因

- 原因 1：前提 2（注册不改源码）是用户明确表达的核心价值，方案 A 直接违背它——每新增一个关注点就要改 core 接口定义。方案 B 的扩展成本是常数（一次注册），不随关注点数量增长。
- 原因 2：前提 3 的两种失败哲学要求分发语义分离。方案 B 用两种语义分别承载，且各自在分发层实现异常包含与 fail-closed；方案 A 与 C 均未处理此对立。
- 原因 3：与 DHS 结构同构，意味着 DHS 验证过的 8 类拦截场景在本机制下均为"注册一个函数"形态，无场景需要改管线。

## 后续影响

- 对代码结构：core/events.py 将承载注册表与两种分发语义的契约；横切关注点（权限、审批、日志、前端推送）以注册方式挂载，不进 core 依赖。
- 对文档：术语表 [CONTEXT.md](../../CONTEXT.md) 是本决策的配套词汇基准；后续设计需引用其词汇，不现场发明近义词。
- 需要后续验证或复盘的事项：
  - "非讨论范围"五项开放问题的逐个决策（建议顺序：槽位覆盖范围 → 链顺序治理 → 事件名封闭性 → 其余分发语义 → 崩溃恢复）。
  - 前提 3（两种失败哲学）在实现层的落实验证：观察槽订阅者故障必须被隔离，拦截链无人应答必须 fail-closed。
  - 前提 1、2 的持续成立：若未来某个关注点无法以注册形态表达，说明本决策的前提失效，需重新评估。
