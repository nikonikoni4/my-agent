# Session 承担过程日志职责（从仅存 Message 到过程日志）

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿 |

## 问题界定

### 问题简述

初始设计仿照 Nanobot，Session 只存储对话消息（user / assistant / tool 消息）。实际调试中发现：出错时很难追踪问题发生的位置和过程。排查依赖 logger，但 logger 与业务事实分离且混杂大量无关信息，调试视图混乱。

### 讨论范围

- Session 模块的职责定位：是"对话消息容器"还是"Agent 处理全过程的日志"。
- 本次只决定方案方向：Session 从仅负责 Message 保存，转向负责整个 Agent 处理过程（从接收消息到最后结束）的日志记录。

### 非讨论范围

- 具体的记录格式、字段设计、信封结构。
- 落盘时机与持久化机制。
- 哪些具体事件类型该记录、哪些不该（如流式 chunk 是否入 session）。
- 与 EventService（运行时事件触发器）的分工细节。

以上均为后续独立的设计决策，不在本 ADR 内展开。

## 现状

- Session 仅存对话消息，无法回答"当前进行到哪一步"。
- 过程信息（轮次、工具调用状态、中断位置）没有结构化落点，调试时只能靠 logger 的时间流文本反推。
- 此前项目经验：同时写 session（业务）和 logger（过程），同一事实两处记录、格式对不上，错误调试时视图混乱。

## 决策前提

- 前提 1：调试追踪困难是真实痛点（亲历：message 与 logger 分离导致排查混乱）。
- 前提 2：DeepSeek-Harness 的 session 设计是生产级验证过的参照（其 session 记录完整处理过程，13 种事件中仅 3 种是对话消息，其余为过程记录）。

## 可选方案

### 方案 A：维持现状（Session 仅存 Message + logger 记录过程）

**优势**

- 改动为零。
- Session 结构简单。

**劣势**

- 过程信息无结构化落点，出错时无法程序化定位"断在哪一步"。
- 同一事实在 session 和 logger 两处记录，格式不统一，调试视图混乱（已亲历）。

### 方案 B：Session 承担过程日志（参照 DeepSeek-Harness）

Session 从"仅存对话消息"扩展为"Agent 全处理过程的结构化日志"：对话消息是日志的子集，过程记录（轮次边界、调用状态等）与消息共同构成完整记录。

**优势**

- 数据高度结构化、无杂质（对比此前 logger 中大量无关信息）。
- 便于读取并生成 HTML 或界面，清晰展示错误位置及详情。
- 可观测性优于 message 与 logger 分开的方法。
- 符合 SSOT（单一事实来源）原则：业务过程只记一份。

**劣势**

- 记录体积随过程数据增长（DeepSeek-Harness 需要专门的打包机制控制）。
- Session 模块职责扩大，实现复杂度高于纯消息容器。

## 决策逻辑

| 前提条件 | 对应方案 | 备注 |
|----------|----------|------|
| 调试可观测性需求成立 + 需要程序化定位问题 | 方案 B | 当前选择 |
| 过程日志的体积/性能成本在实际运行中不可接受 | 收缩记录范围（仅记录边界与配对等低频事实，不记录高频过程数据） | 备选触发条件 |

## 最终决策

当前成立的前提：调试追踪困难是真实痛点；DeepSeek-Harness 已验证该模式的可观测性收益。

因此选择 `方案 B：Session 承担过程日志`。

前提失效时的切换路径：若过程日志的体积或性能成本不可接受，收缩记录范围而非回退到 message + logger 分离方案（结构化与 SSOT 的收益仍需保留）。

## 决策原因

- 调试追踪困难直接源于过程信息无结构化落点，方案 B 在记录层面消除该问题，对应问题界定。
- 结构化日志可程序化检查完整性（如调用配对），优于 logger 的人工 grep 排查。
- 业务过程只记一份，消除 message 与 logger 双记录的混乱，符合 SSOT 原则。

## 后续影响

- 具体记录内容、格式、信封结构需要独立的设计决策（本 ADR 明确不覆盖）。
- 流式 chunk 等高频过程数据是否入 session 需单独评估（本项目 EventService 与 Session 是分开的模块，与 DeepSeek-Harness"存储与分发同管道"的前提不同）。
- 日志体积增长问题记录为已知限制，出现实际影响时再处理（打包、截断等），不预先建设。
