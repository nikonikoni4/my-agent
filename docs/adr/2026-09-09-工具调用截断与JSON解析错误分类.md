# 工具调用截断与 JSON 解析错误分类

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿（决定：`LLMToolCallParseError` 与 `LLMToolCallTruncatedError` 平铺并列，不父子归类） |

## 问题界定

### 问题简述

工具调用的 `arguments` 在 `json.loads` 时可能解析失败。已确立两种错误来源：

- `LLMToolCallTruncatedError`：`finish_reason == 'length'`，输出达到 `max_tokens` 被截断，arguments 的 JSON 在生成中途被切断。
- `LLMToolCallParseError`：非截断的非法 JSON（单引号、括号不匹配、多余逗号等），模型生成了语法非法的参数。

两者表层都表现为"arguments 解析失败"，决策问题：它们在异常分类树里应**平铺并列**，还是把截断**归类为解析错误的子类**。

### 讨论范围

- 这两类异常在分类树（`LLMCallError` 之下）的形态：并列 or 父子。
- 二者的处置入口与提示层级是否应分离。

### 非讨论范围

- 具体的 `max_tokens` 数值、提示词措辞、loop 恢复代码细节——留待后续独立决策。
- 除这两类之外的其它可恢复/不可恢复策略映射——属于独立的策略注册表设计。

### 模糊信息的明确定义

- **非法 JSON（Parse）**：`JSONDecodeError`，结构语法错误，与输入长度/配额无关。
- **截断（Truncated）**：`finish_reason == 'length'`，语义上"没写完"，参数结构本来合法但被切断。

### 问题深度

涉及异常分类树的形态与"错误来源 vs 致命程度如何指导分层"的架构原则问题，影响长期维护与错误治理体验。

## 现状

- `execption.py` 已有来源分类树：`LLMCallError` 为基类，`LLMToolCallTruncatedError` 已在其中；本次新增 `LLMToolCallParseError`，目前为平铺并列。
- `provider.parse_tool_call` 与 `openai_provider` 流式拼装处已分别用 try/except 捕获 `JSONDecodeError` 并包装为对应的领域异常；截断场景由 `check_truncated_tool_calls` 抛 `LLMToolCallTruncatedError`。

## 决策前提

- 前提 1：两类错误**表层同构**（都是 `json.loads` 失败），但**根因层级不同**。
- 前提 2：截断的根因常是**系统配置 / 提示词 / 工具参数体量**等宏观因素，而非工具参数"写错"。
- 前提 3（用户判断）：截断**更致命、更易被忽略、很多人处理不好**，需要特别关注与专门提示，重要性高于普通 JSON 解析错误。
- 前提 4：若二者父子归类，捕获父类会把子类一起吞掉，**无法在 `except` 层把截断与普通解析分开处置**。
- 前提 5（对齐现有分类树原则）：分类按"错误来源"，恢复策略由独立策略注册表决定，类型只标注来源。

## 可选方案

### 方案 A：平铺并列（选定）

`LLMToolCallParseError(LLMCallError)` 与 `LLMToolCallTruncatedError(LLMCallError)` 各自直接继承基类，互不父子。

**优势**

- `except` 层可把截断与普通解析分开，分别登记不同恢复策略、给不同提示。
- 截断获得与其重要性匹配的"独立类型身份"。
- 与"按来源分类 + 独立策略注册表"原则一致。

**劣势**

- 多出两个顶层来源类型；需维护"什么算截断、什么算解析"的边界理解。

### 方案 B：截断作为解析错误的子类（否决）

`LLMToolCallParseError` 为父，`LLMToolCallTruncatedError` 继承它，统称"解析失败"。

**优势**

- 语义上两者确实都是"arguments 解析失败"。

**劣势**

- 捕获父类 `LLMToolCallParseError` 时会把截断一并吞掉，无法在 `except` 层区分处置（违反前提 3、4）。
- 把"更重要、更需专门提示的截断"降格为普通解析失败的子类，与其实际重要性不匹配（违反前提 2、3）。

## 决策逻辑

| 前提条件 | 对应方案 | 备注 |
|----------|----------|------|
| 前提 3 + 4 成立（截断更重要、需分开处置） | 方案 A | 当前选择 |
| 追求"都是解析失败"的统一捕获、且接受处理重要性不同的场景时被合并 | 方案 B | 备选触发条件 |
| 出现证据表明截断其实可以按普通解析方式处置（无需特殊提示） | 收敛为方案 B | 防御性调整 |

## 最终决策

当前成立的前提：前提 1—5。因此选择 **方案 A**：`LLMToolCallParseError` 与 `LLMToolCallTruncatedError` 平铺并列，各自直接继承 `LLMCallError`，分别处置。

前提失效时的切换路径：见决策逻辑表。若后续实证截断可按普通解析方式处置，则收敛为方案 B。

## 决策原因：突出 Max Token（截断）的重要性

普通 JSON 解析错误与截断不在一个治理层级，原因在于截断存在**三点超出工具写法本身的重要性**，须与普通解析分开：

### 1. 系统配置问题（Max Tokens 配置）

`max_tokens` 配置过低，导致模型在合法输出完整 arguments 之前就被截断。这属于**系统配置层面**，不是模型写错了参数。

- 处置：出现此类错误应**提示用户调整配置（调大 `max_tokens`）**，而非当作普通参数错误重试。
- 普通解析错误没有这一治理维度，正是必须分开的原因之一。

### 2. 工具参数不合理（体量触发）

工具的某个参数体量过大时，也可能把输出顶到 `max_tokens`。典型示例：Claude Code 中的 `write` 工具，`content` 写入内容过多会触发 Max Token 限制。

- 这类情况工具**本身没有写错**，是"单次调用体量超出上限"，需要给特殊提示，例如**建议减少单次写入内容、拆分写入**，而不是简单重试。
- 现实中可能存在其它与工具效用相关的类似体量限制，处置上属于"工具参数不合理导致的截断"分支。

### 3. 提示词限制（前置治理）

截断的第三个来源是提示词未约束输出量。应在**提示词中明确调用工具或输出时的限制条件**（如内容长度、单次写入上限、参数规模），从源头降低截断概率。

- 这是治理手段而非事后补救，同样只适用于"截断"这一来源。

### 小结

三点重要性（配置层 / 工具参数体量层 / 提示词层）都指向**同一根因——输出超过了 `max_tokens` 的承载能力**，与"模型产出了非法 JSON"的普通解析错误并列它会丧失治理表达力。因此二者平铺，分别给不同类型、不同恢复策略：截断走"提示改配置 / 减量 / 改提示词"，普通解析走"把 raw_arguments + JSONDecodeError 回喂模型重新生成"。

## 后续影响

- 后续任务（独立设计）：在 `loop` 或策略注册表中分别为 `LLMToolCallTruncatedError`（提示改配置 / 减量 / 改提示词）与 `LLMToolCallParseError`（回喂参数重新生成）登记不同恢复动作。
- 截断提示建议沉淀：改 `max_tokens` 配置、建议减少单次写入内容、在提示词中补充输出/工具调用限制。
- 普通解析提示建议：把未解析的 `raw_arguments` 与 `JSONDecodeError` 信息（位置/原因）回喂模型，诱使其产出合法 JSON 后重试。
- 三类截断成因（配置 / 工具参数体量 / 提示词）可后续落在面向用户的可操作文案，作为独立设计。
