| 2026-09-15 | [agent loop 错误处理重构](.\2026-09-15-agent-loop错误处理重构.md) | 用户在错误处理结构决策上展现了"以可维护性定形态、按代价排序取舍"的判断模式：(1) 目标先行——要求"循环里全部捕获 + 一处集中处理"，使改策略不动主框架；(2) 主动砍掉复杂路径——提出"只留 2 个 except（取消 + 兜底）、在 finally 内处理"的形态，并否掉"循环外预检配置错误"（自认与初心相悖）；(3) 用"未来会不会改主框架"检验方案——明确"现在统一停 turn、将来想到再区分"，据此要求形态支持"将来区分不动主框架"；(4) 代价算得很细——在"加一个标志位"与"多一条空 step 记录"之间选前者，理由是空记录会污染统计；以"每次错误可能不同"为由要求"最后一类失败也落记录"；(5) 逐条校正 AI 的论证前提——指出 AI 的"后果"多建立在代码未完成之上、要求只讲功能后果，并以"取消不会失灵""日志在处理前已记"否掉两条推论。 | 适用于错误处理、控制流形态、记录一致性类决策。用户先立目标（改策略不动主框架 / 终态可靠），再按"代价落在哪"排序取舍，并会主动校正 AI 论证所依赖的前提。 | AI 曾给出三条"后果"，两条建立在未完成代码之上——后续 agent 不要把"当前实现不完整"当成设计缺陷。`finally` 内 `break` 的安全依赖"分支互斥"（except 已吞异常 + 取消路径只 raise），新增分支时必须复核，否则会静默吞掉在途异常。 |
| 2026-09-15 | [异常分类树新增策略域与未知域](.\2026-09-15-异常分类树新增策略域与未知域.md) | 用户在异常分类树设计上展现了"用判据把域切干净、宁窄勿宽"的判断模式：(1) 以既有设计规则为准绳——主动指出现有树的分类主轴是"错误来源而非错误处理"（否则处理一变就得动类型），并据此判定"循环自身判定的错误既不属于 llm call 也不属于 tool result"，必须新立一域；(2) 面对"新域装什么"，用"性质是否同类"切分——AI 提出宽域方案（策略判定 + 编排层未归因异常一并装）后，用户采纳"两者性质相反（确定可枚举 vs 兜底）"的分析，选择窄域 + 独立兜底，宁可多一个域也不混装；(3) 关注命名的可判别性——主动要求名字"更精确"（表示策略错误或编排错误），并在候选间选择了语义更稳的 AgentPolicyError 而非更字面的 AgentLimitError；(4) 对既有遗留类型给出明确处置——判定 LLmError 的旧语义（request/error 无人认领）本身是流程决策而非来源，应改名换职务为"未知错误"，而非留着不动。 | 适用于异常分类树、错误域划分、类型命名类决策。用户会先确认既有树的划分判据，再用"性质是否同类"决定成员归属，并坚持"域必须可枚举、判据唯一"；对遗留类型倾向"换职务"而非"保留并存"。 | AI 上一轮曾建议"未归因异常包成 AgentLoopError"，与用户"策略域取窄"的取向相反——后续 agent 不要把兜底逻辑塞进语义明确的域。"一级域 = 终结路径"这一判据是本次固化的，若将来出现"跨多条路径才终结"的错误，需重新审视判据。`LLmError` 改名会波及 loop 抛错点与测试引用，落地时不可漏改。 |
| 2026-09-15 | [session 错误信息记录策略](.\2026-09-15-session错误信息记录策略.md) | 用户在"日志可诊断性"决策上展现了"以诊断目的反推记录形态 + 用一致性否决局部优化 + 连续追问落地代价"的判断模式：(1) 起点是明确的目的判据——"session 即日志"，只读 session 就要能快速找到错误，据此判定"只记 str 不够"，要能看出错误类别；(2) 主动收窄完备性——只记"错误类别 + 错误信息"，并给出可校验的依据：当前唯一的多层错误是 LLM 重试，而重试有独立的 llm/retry 可在发生点承载原始信息，故终态无需跟踪下一层；(3) 用事实界定边界——确认错误链最长 3 层后直接定 cap=3；(4) 纠正 AI 的过度告警——AI 提出"ExceptionGroup 走不进子异常"的坑后，用户以"这里不是已经 split 出 ToolConsecutiveFailureError 了吗"指出 AI 把"容器"与"链"混为一谈，该坑在原表述下并不适用于熔断路径；(5) 连续追问 AI 方案的落地代价——"至少要增加 6 行写事件？"、"你的补究竟是补什么？"，要求把抽象描述落到具体字段与 jsonl 形态后才做判断；(6) 用反例检验方案——提出"如果每次 llm 重试错误不一样呢"，直接推翻 AI 原先"收尾不记"的建议，并以"一致的处理方式既符合认知代码也简单，唯一缺点只是多了一个冗余的字符串"点出取舍实质。 | 适用于日志/可观测性/错误记录形态类决策。用户会先立"只读日志能否定位问题"的判据，再决定记什么字段；对"每次发生是否同构"敏感，倾向用一致性换掉局部最优；且要求把方案的代价具体化到字段与记录形态再拍板。 | 用户会主动推翻 AI 的建议（本决策中 AI 先推荐"收尾不记"、随后撤回并改为"都记"），后续 agent 不应把此处结论当不可动摇的契约，应关注推导依据。"只记类别 + 消息"的收窄依赖"重试是唯一多层错误"这一当前事实，若将来出现新的多层错误，终态是否需要跟踪下一层需重新评估。"限深 3 层"同样绑定当前最大链长，新增包装层后需复核。 |
| 2026-09-10 | [cancel 取消并结束循环](.\2026-09-10-cancel取消并结束循环.md) | 用户在组件生命周期/并发语义决策上展现了"机制实测 → 与运行时契约对齐 → 主动推翻自己的方案"的判断模式：(1) 通过实测确认 cancel 的投递时机（只是登记请求、投递发生在下一轮事件循环、调用方不让出就永不投递），并进一步确认"吞掉取消"会让所有等待 loop task 结束的外部机制（asyncio.run 收尾、wait_for 超时、gather、SIGINT、测试 teardown）永久挂起；(2) 越过局部实现上溯语言设计动机——CancelledError 自 3.8 起继承 BaseException 正是为了阻止 except Exception 兜底吞掉取消，据此判定"吞掉取消"与 asyncio 契约相悖；(3) 因此主动推翻自己先前拍板的"cancel 不打断循环 + stop"拆分方案，改为 cancel 恢复"取消并结束循环"，理由是"尽量还是和它原设计对齐，避免可能的不兼容问题"；(4) 明确要求传播链显式化——最内层 step 必须 raise、中间 turn 必须 raise、最外层 _loop 捕获后 break，并准确预判"吞掉取消后 while 不会自己停，必须显式 break"；(5) 保留取消"作废排队消息"的既有边界，并给出恢复路径——send 是唯一入口，判定循环未运行则自动重启，理由是"它停下来反而还是节约资源"。 | 适用于 agent 生命周期/并发原语语义决策，尤其是"组件语义与承载它的运行时（asyncio）契约是否一致"这类问题。用户会先用实测确认机制事实，再上溯到语言/运行时设计的动机，最后以"与运行时对齐"为准绳推翻自己此前的方案。 | 该用户会主动推翻自己的先前决定（决策可被更强前提修正），后续 agent 不要把他先前的结论当作不可动摇的契约，应关注推导依据。不要因为"取消后需重启循环"这类局部使用成本，保留任何会吞掉 CancelledError 的设计。cancel 现在必然结束循环，"只打断当前工作、保留循环与排队消息"不再是现成能力，若将来确需该语义，应另设独立手段而非复用 cancel。 |
| 2026-09-10 | [工具调用解析与截断处置移入工具层](.\2026-09-10-工具调用解析与截断处置移入工具层.md) | 用户在错误处置归属决策上展现了"发生阶段 + 信息归属定层 + 目的语义定义机制"的判断模式：(1) 核心判据是"输出是否已完成"——解析失败发生在 usage、finish_reason 都返回之后，故不算 LLM 调用错误，严格按发生阶段而非处理便利归层；(2) 三连纠偏 AI 方案，每次都以职责归属为由（provider 抛异常→"这是输出后处理，不是调用错误"；raw_arguments union→"没必要，直接在工具层解析"；截断话术放 loop→"写错地方了，不能写在 loop 内"），并亲手补齐 finish 块机制让截断强调有了新载体；(3) 以机制的目的而非失败归因定义计数语义——熔断"是为了避免模型反复调用一个工具一直出错，既包括模型出错也包括工具出错"，纠正了 AI 按"不是工具的错"排除模型侧失败的判断。 | 适用于 agent 各层职责划分、错误分类、熔断/降级语义设计。用户会用"错误发生在哪个阶段、信息天然归谁拥有"划层，用机制目的反推计数/参数语义。 | "按语义归属划层"教条化可能把边界校验拆散，应保留工程便利的权衡空间；熔断计入模型侧失败意味着坏输出会消耗健康工具的可用额度（阈值内靠自纠清零），需观测自纠率与熔断误伤。 |
| 2026-09-09 | [工具调用截断与 JSON 解析错误分类](./2026-09-09-工具调用截断与JSON解析错误分类.md) | 在延续"错误来源分类树"前提的同时，用户展现了"用根因层级 + 致命程度指导异常分层"的模式：(1) 元认识上的纠偏——虽然我一直提示"截断本质是解析失败"，但用户明确拒绝把截断当作普通 JSON 解析错误的子类，理由是两者根因层级不同（截断源于 system 配置/提示词/工具参数体量，解析仅工具写法）；(2) 以"致命程度 + 易被忽略性"为重要性排序标准——亲历过该问题，认定截断更致命、很多人处理不好，应获得与重要性匹配的独立类型身份和专属提示；(3) 拆解出截断的三类成因（配置过低 / 工具参数体量过大如 write 单次写太多 / 提示词未约束输出），并各自给出治理动作（提示改配置 / 减量 / prompt 前置约束）；(4) 用"父子归类会让 except 无法区分处置"这一机制性理由否定合并。判断主轴：分类分层不只看"表面属不属于同类"，更看"根因层级、致命程度、处置方式是否可分"。 | 适用于 agent 错误分类树、治理文案、恢复策略设计时兼顾"来源 + 严重度"两个维度。用户会拒绝纯语义归类（同为解析失败），重视坑位的可操作提示设计。 | "严重度优先分层"若泛用会导致分类树按严重度无限细分；应保持来源为主轴、严重度只体现在处置文案与策略，不为其扩张类型（呼应 LLM 错误处理 ADR 的防御性调整行）。 |

## 决策偏好总结

- 痛点驱动决策：方案转向的触发点是亲历的调试困难，而非理论推演
- 参照系统的架构前提先于结论：借鉴前先核实参照实现（DeepSeek-Harness）的设计前提是否与本项目一致，前提不同则结论不同
- 方案决策与具体设计严格分层：ADR 只记方向决定，格式、字段、取舍留给独立设计决策
- **分类放在源码分层边界处**：SDK 原始异常在 LLM 层内部翻译成领域异常，agent 内核只做单点捕获；分类主轴按"错误来源"建异常分类树
- **错误分类按发生阶段与信息归属定层**：判断"是不是调用错误"的硬判据是"输出是否已完成"（usage/finish_reason 是否已返回）——输出后的内容问题归工具层回喂自纠，流中断归 LLM 错误路径；响应级信息（finish_reason）由拥有它的 provider 翻译成调用级标记（truncated），消费方据此处置，loop 只编排
- **机制语义按目的定义而非按归因**：熔断的目的是防"模型反复调用一个工具一直出错"，模型侧写坏参数与工具侧执行失败同等计数，不因"不是工具的错"而排除
- **按变化频率分离稳定与易变**：来源稳定、重试策略易变，把重试策略从异常类型上剥离放入独立策略注册表（异常类型→策略），避免"改策略要动类型树"；判断标准是信息变动的频率是否不同
- **极端路径追问优先于表面完整**：AI 给出方案后，主动构造"方案自身也失败"的场景（回滚时文件也打不开）检验完备性，并以自己的修正方案补全设计，而非直接接受或全盘推翻
- **决策后三步固化：业界核实 → 教程沉淀 → ADR + 测试锁定**：可靠性决策不留口头结论，用失败注入测试锁定行为边界，用教程和 ADR 双载体沉淀
- **接受测试注入替身而非强求真实环境复现**：理解真实 OS 锁/磁盘满无法稳定复现后，接受在 OS 抛错入口注入异常的确定性测试做法
- **与承载运行时的契约一致优先于局部便利**：取消语义对齐 asyncio 原设计——取消即结束循环，取消异常一路传播到最外层消化；不为了"取消后免重启"这类使用便利去吞掉取消（吞掉会让等 task 结束的外部机制永久挂起，且与 CancelledError 提升为 BaseException 的动机相悖）。判断标准：组件语义是否与它运行的并发模型契约一致
- **决策可被更强前提推翻并显式记录反转**：发现"吞掉取消与 asyncio 契约冲突"这一更强前提后，主动推翻先前拍板的拆分方案并重写 ADR（v1.0 → v2.0），保留演进历史；不因"已经定了"而保留原结论
- **先实测机制再下判断**：对并发/取消这类"行为取决于时序"的机制，先写最小脚本实测其确定行为（投递时机、异常落点），用事实判定问题性质是竞态还是实现疏漏，再进入方案讨论
- **以诊断目的反推记录形态**：先立"只读日志能否定位问题"的判据，再决定记哪些字段——错误记录主张"记类别 + 信息"而非裸 str；当"每次发生是否同构"受影响时，用一致性（每次失败都落一条）优先于"少一条记录"的局部优化，判断依据是认知负担与代码简洁，而非记录体积
- **域划分宁窄勿宽，判据先写死**：新建分类域之前先立唯一判据（如"域 = 错误在哪条路径被产生/终结"），再决定成员归属；确定性的域（策略判定）与兜底（归因失败）必须分开——宁可多一个域，也不让兜底摊薄确定域的判别力；对遗留类型倾向"改名换职务"而非保留并存

## 给后续 agent 的参考

- 设计 session/日志/可观测性相关功能时，业务过程事实只记一份（SSOT），logger 只记 session 表达不了的技术细节（堆栈、重试、基础设施故障）
- 引用 DeepSeek-Harness 的做法前，先确认其架构前提（如"存储与分发同管道"）在本项目是否成立；本项目 EventService 与 Session 是分开的模块
- 不要在本 ADR 基础上直接展开具体设计（记录格式、chunk 取舍等），这些是待做的独立决策
- 实现 session 加载逻辑时的崩溃修复（残缺尾巴）是独立决策，届时参考教程 0004 第 7 节的业界方案（每行 CRC 自描述）；不要沿用两级回滚的内存回滚目标——进程崩溃即丢
- 修改 persistence.py 的失败处理逻辑前，先读 tests/agent/core/test_persistence.py：8 个失败场景测试是行为契约，包含"文件被长期占用"的极端场景
- 多写者场景出现时，两级回滚方案不可沿用（单写者前提失效），需独立决策文件锁或后端更换
- SessionPresist 写 meta 时必须落盘 cwd，这是 2026-09-07 文件夹命名 ADR 读取分组方案的前置依赖
- 实现会话分组/UI 列表时按"扫描每个 {session_id}.jsonl 第一行 meta"实现；扫描成为瓶颈时按该 ADR 决策逻辑表切换 index.json 或 SQLite
- provider 不做工具参数 JSON 解析是有意为之（见 2026-09-10 工具调用解析 ADR）：`RawToolCall.arguments` 恒为 wire 原样字符串，解析/校验/hint 回喂都在 `ToolRegister`（信任边界）；不要把 json.loads 挪回 provider，也不要给 arguments 加 dict 分支或给 loop 加截断话术特判
- 读取会话时建议补 meta cwd 与所在文件夹的一致性校验（当前未实现，无校验时撞车静默发生）
- 结束/取消 agent 用 `cancel()`：语义是"取消在途 turn + 作废排队消息 + 结束循环"（见 2026-09-10 cancel 取消并结束循环 ADR）；循环停止后由 `send()` 按需自动重启，不要再引入 `stop()` 或停止标志
- 不要在 turn/step 内吞掉 `CancelledError`：step 记 interrupted 后必须 `raise`、turn 同样 `raise`，由 `_loop` 最外层统一 warning + break；吞掉取消会让 asyncio.run 收尾、`wait_for`、测试 teardown 等等待方永久挂起。测试收尾同理，见 `tests/agent/core/test_loop_paths.py` 的 `shutdown()`
