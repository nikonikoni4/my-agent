# User Design Summary

## 目的

记录用户在重大设计决策中的偏好、判断方式和风险倾向，为后续 agent 自主决策提供参考，也为用户复盘决策方式提供材料。

| 2026-09-09 | [工具调用截断与 JSON 解析错误分类](./2026-09-09-工具调用截断与JSON解析错误分类.md) | 在延续"错误来源分类树"前提的同时，用户展现了"用根因层级 + 致命程度指导异常分层"的模式：(1) 元认识上的纠偏——虽然我一直提示"截断本质是解析失败"，但用户明确拒绝把截断当作普通 JSON 解析错误的子类，理由是两者根因层级不同（截断源于 system 配置/提示词/工具参数体量，解析仅工具写法）；(2) 以"致命程度 + 易被忽略性"为重要性排序标准——亲历过该问题，认定截断更致命、很多人处理不好，应获得与重要性匹配的独立类型身份和专属提示；(3) 拆解出截断的三类成因（配置过低 / 工具参数体量过大如 write 单次写太多 / 提示词未约束输出），并各自给出治理动作（提示改配置 / 减量 / prompt 前置约束）；(4) 用"父子归类会让 except 无法区分处置"这一机制性理由否定合并。判断主轴：分类分层不只看"表面属不属于同类"，更看"根因层级、致命程度、处置方式是否可分"。 | 适用于 agent 错误分类树、治理文案、恢复策略设计时兼顾"来源 + 严重度"两个维度。用户会拒绝纯语义归类（同为解析失败），重视坑位的可操作提示设计。 | "严重度优先分层"若泛用会导致分类树按严重度无限细分；应保持来源为主轴、严重度只体现在处置文案与策略，不为其扩张类型（呼应 LLM 错误处理 ADR 的防御性调整行）。 |
| 2026-09-09 | [LLM 错误处理分类策略](../adr/2026-09-09-LLM错误处理分类策略.md) | 用户在错误处理分层上展现了"边界前置 + 分类形态演进 + 按变化频率分离"的判断模式：(1) 决策起点是"在哪里识别分类"（provider 内部 vs loop 内），主动把分类放在源码边界（LLM 层）完成 SDK 异常 → 领域异常翻译；(2) 以"最终错误处理集中一处，分散捕获会重复归集判断"否决分散方案；(3) 分类维度先倾向"处理角度"（按重试动作分 3 类），随后主动转到"来源角度"，理由是按来源分类 + 独立策略注册表时，"发现某错误其实可重试"只改注册表一行、异常树一个类都不用动——本质是**把稳定（来源）与易变（重试策略）分开，策略不焊死在类型上**；(4) 严格划定决策边界：本次只记"方向 + 分类树策略"，具体来源子类清单后续按需补充。 | 适用于 agent 分层边界（LLM/Tool/内核）上的错误处理策略决策。用户倾向在源码分层边界完成异常翻译，并习惯检视"哪个信息稳定、哪个易变"，把易变信息剥离到独立配置/映射，避免高频修改触碰低频结构。 | "来源分类 + 独立策略注册表"里，来源子类粒度未实证、策略注册表尚未实现（ADR 已列为后续任务）；后续 agent 落地时注意分类树粒度（见 ADR 决策逻辑防御性调整行）。当前 provider 仍统一抛基类，需补按来源映射到具体子类。 |
| 2026-09-04 | [Session 持久化写入两级回滚](.\2026-09-04-session持久化写入两级回滚.md) | 用户在写入原子性决策上展现了"极端路径追问 + 参照权威实现 + 失败路径测试化"的模式：(1) 不接受 AI 首版方案的表面完整，主动追问"回滚时文件也打不开怎么办"，发现尽力而为回滚的基线固化漏洞，并自己提出修正方案（记住写前大小，下次写入前先补截断）——该方案恰与 SQLite 回滚日志同型；(2) 主动要求联网检索业界做法核实方向，确认 torn write 是有标准解法的经典问题后才固化决策；(3) 要求用"文件被长期占用"的极端场景写测试验证，在理解真实 OS 锁无法稳定复现后接受契约边界注入的测试替身；(4) 明确划定边界：崩溃级恢复列为已知限制不在当前决策处理，fsync 不纳入范围。 | 适用于写入类基础设施（日志、持久化、缓存落盘）的可靠性决策。用户会追问"恢复动作自身失败怎么办"，并以失败注入测试作为验收标准。 | 两级回滚依赖单写者前提（用户已确认），多写者出现时方案不可沿用；内存回滚目标在进程崩溃时丢失，加载侧崩溃修复将来必须独立决策。 |

## 决策偏好总结

- 痛点驱动决策：方案转向的触发点是亲历的调试困难，而非理论推演
- 参照系统的架构前提先于结论：借鉴前先核实参照实现（DeepSeek-Harness）的设计前提是否与本项目一致，前提不同则结论不同
- 方案决策与具体设计严格分层：ADR 只记方向决定，格式、字段、取舍留给独立设计决策
- **分类放在源码分层边界处**：SDK 原始异常在 LLM 层内部翻译成领域异常，agent 内核只做单点捕获；分类主轴按"错误来源"建异常分类树
- **按变化频率分离稳定与易变**：来源稳定、重试策略易变，把重试策略从异常类型上剥离放入独立策略注册表（异常类型→策略），避免"改策略要动类型树"；判断标准是信息变动的频率是否不同
- **极端路径追问优先于表面完整**：AI 给出方案后，主动构造"方案自身也失败"的场景（回滚时文件也打不开）检验完备性，并以自己的修正方案补全设计，而非直接接受或全盘推翻
- **决策后三步固化：业界核实 → 教程沉淀 → ADR + 测试锁定**：可靠性决策不留口头结论，用失败注入测试锁定行为边界，用教程和 ADR 双载体沉淀
- **接受测试注入替身而非强求真实环境复现**：理解真实 OS 锁/磁盘满无法稳定复现后，接受在 OS 抛错入口注入异常的确定性测试做法

## 给后续 agent 的参考

- 设计 session/日志/可观测性相关功能时，业务过程事实只记一份（SSOT），logger 只记 session 表达不了的技术细节（堆栈、重试、基础设施故障）
- 引用 DeepSeek-Harness 的做法前，先确认其架构前提（如"存储与分发同管道"）在本项目是否成立；本项目 EventService 与 Session 是分开的模块
- 不要在本 ADR 基础上直接展开具体设计（记录格式、chunk 取舍等），这些是待做的独立决策
- 实现 session 加载逻辑时的崩溃修复（残缺尾巴）是独立决策，届时参考教程 0004 第 7 节的业界方案（每行 CRC 自描述）；不要沿用两级回滚的内存回滚目标——进程崩溃即丢
- 修改 persistence.py 的失败处理逻辑前，先读 tests/agent/core/test_persistence.py：8 个失败场景测试是行为契约，包含"文件被长期占用"的极端场景
- 多写者场景出现时，两级回滚方案不可沿用（单写者前提失效），需独立决策文件锁或后端更换
- SessionPresist 写 meta 时必须落盘 cwd，这是 2026-09-07 文件夹命名 ADR 读取分组方案的前置依赖
- 实现会话分组/UI 列表时按"扫描每个 {session_id}.jsonl 第一行 meta"实现；扫描成为瓶颈时按该 ADR 决策逻辑表切换 index.json 或 SQLite
- 读取会话时建议补 meta cwd 与所在文件夹的一致性校验（当前未实现，无校验时撞车静默发生）
