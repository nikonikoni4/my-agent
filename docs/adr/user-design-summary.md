## 目的

记录用户在重大设计决策中的偏好、判断方式和风险倾向，为后续 agent 自主决策提供参考，也为用户复盘决策方式提供材料。

## 决策偏好总结

- 痛点驱动决策：方案转向的触发点是亲历的调试困难，而非理论推演
- 参照系统的架构前提先于结论：借鉴前先核实参照实现（DeepSeek-Harness）的设计前提是否与本项目一致，前提不同则结论不同
- 方案决策与具体设计严格分层：ADR 只记方向决定，格式、字段、取舍留给独立设计决策
- **极端路径追问优先于表面完整**：AI 给出方案后，主动构造"方案自身也失败"的场景（回滚时文件也打不开）检验完备性，并以自己的修正方案补全设计，而非直接接受或全盘推翻
- **决策后三步固化：业界核实 → 教程沉淀 → ADR + 测试锁定**：可靠性决策不留口头结论，用失败注入测试锁定行为边界，用教程和 ADR 双载体沉淀
- **接受测试注入替身而非强求真实环境复现**：理解真实 OS 锁/磁盘满无法稳定复现后，接受在 OS 抛错入口注入异常的确定性测试做法

## 给后续 agent 的参考

- 设计 session/日志/可观测性相关功能时，业务过程事实只记一份（SSOT），logger 只记 session 表达不了的技术细节（堆栈、重试、基础设施故障）
- 引用 DeepSeek-Harness 的做法前，先确认其架构前提（如"存储与分发同管道"）在本项目是否成立；本项目 EventService 与 Session 是分开的模块
- 不要在本 ADR 基础上直接展开具体设计（记录格式、chunk 取舍等），这些是待做的独立决策
- 实现 session 加载逻辑时的崩溃修复（残缺尾巴）是独立决策，届时参考教程 0004 第 7 节的业界方案（每行 CRC 自描述）；不要沿用两级回滚的内存回滚目标——进程崩溃即丢
- 修改 persistence.py 的失败处理逻辑前，先读 tests/agent/core/test_persistence.py：8 个失败场景测试是行为契约，包含"文件被长期占用"的极端场景
- 多写者场景出现时，两级回滚方案不可沿用（单写者前提失效），需独立决策文件锁或后端更换
- SessionPresist 写 meta 时必须落盘 cwd，这是 2026-09-07 文件夹命名 ADR 读取分组方案的前置依赖
- 实现会话分组/UI 列表时按"扫描每个 {session_id}.jsonl 第一行 meta"实现；扫描成为瓶颈时按该 ADR 决策逻辑表切换 index.json 或 SQLite
- 读取会话时建议补 meta cwd 与所在文件夹的一致性校验（当前未实现，无校验时撞车静默发生）
