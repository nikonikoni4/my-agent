# session 错误信息记录策略

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿 |
| 1.1 | 重写「决策前提」：改为当前成立的事实与约束（原版把决策内容误写成前提）；决策逻辑表同步改为"前提 → 决策 → 失效切换" |

## 问题界定

### 问题简述

session 已承担过程日志职责（见 2026-09-03 ADR），但错误路径只把 `str(异常)` 写进 `step/end` / `turn/end` 的 `reason_text`。实测中同一条错误落进 session 的形态并不稳定：可能是底层库的裸文本（`peer closed connection without sending complete message body`），也可能是被上层包装后的摘要。结果是**只看 session 既看不出错误属于哪一类，也无法回溯根因**——与"session 即日志、只读 session 即可定位错误"的目标不符。

### 讨论范围

- 错误进入 session 的形态：记哪些字段。
- 异常链（叠层包装）在 `reason_text` 中如何呈现。
- 唯一多层错误（LLM 重试）的原始信息落在哪里。

### 非讨论范围

- 错误在 loop 内如何被捕获、重试、终止（含 `turn/end = error` 的语义判定）——另行决策。
- 错误类别的具体枚举清单与命名。
- 各错误类别对应的恢复策略。
- `request/error` 事件的订阅方与决策链。

### 模糊信息的明确定义

- **终态错误**：使当前 turn 结束的错误。本 ADR 只讨论其**记录形态**，不讨论判定规则。
- **发生点记录**：在错误实际产生的那一层落下的结构化记录（此处特指 LLM 重试路径）。

### 问题深度

属可观测性原则在存储层的落地：决定"日志能不能用来诊断"，影响 session 记录格式及其后续消费方（评估、统计、人工排查），是长期维护方式层面的决策。

## 现状

- session 已承担过程日志职责（2026-09-03 ADR）。
- 错误路径的终态只有 `reason_text` 一个字符串字段，没有类别字段。
- LLM 重试已有独立记录 `llm/retry`（`retry_count` + `reason`），但**不含触发重试的错误本身**，只记"第几次重试、什么决策"。
- 工具失败本身以 `ToolResult` 落在 `tool/result`（`is_error=True`），不依赖异常链承载。

## 决策前提

前提是**当前成立的事实与约束**（非决策内容）；它们成立才推出本决策，失效则应切换方案（见"决策逻辑"）。

- 前提 1（既有约束，2026-09-03 ADR）：session 是唯一的过程日志，诊断错误只能依赖 session。因此"只读 session 能定位错误"是硬需求。
- 前提 2（现状事实）：错误路径的终态目前只有 `reason_text` 一个字符串字段，没有承载错误类别的字段。
- 前提 3（实测事实）：当前错误链最长 3 层——`httpx.*` → `LLMConnectionError` → `LLmError`；`openai.APIError` → `LLMCallError` → `LLmError`。
- 前提 4（现状事实）：本仓库的错误包装一律为显式 `raise ... from e`，未使用隐式 `__context__` 链。
- 前提 5（实测事实）：`ExceptionGroup` 是容器而非链——TaskGroup 产出的 group，其 `__cause__` 与 `__context__` 均为 `None`（`suppress_context=True`），只沿 `__cause__` 遍历只能得到 `unhandled errors in a TaskGroup`。
- 前提 6（现状事实）：当前能击穿到 turn 终态的错误共 6 类（超过最大步数 / LLM 重试耗尽 / 取消 / 超时 / 工具熔断 / 工具组其他错误），其中**只有 LLM 重试**的终态是"多次失败汇总"，其余 5 类的终态就是错误本身、没有下层根因。
- 前提 7（现状事实）：LLM 重试已有独立记录通道 `llm/retry`（`retry_count` + `reason`），但其中不含触发重试的错误本身。
- 前提 8（现状事实）：工具失败以 `ToolResult` 落在 `tool/result`（`is_error=True`），其原始信息不依赖异常链承载。
- 前提 9（**假设**，待观察）：每次重试的错误可能不同（类型与内容都可能变化）。
- 前提 10（需求约束）：`error_type` 的消费方目前是人（快速定位）与评估脚本（粗粒度过滤），尚无"按根因聚合统计"的需求。

## 可选方案

### 方案 A：终态记「类别 + 异常链文本」，重试每次失败都落记录（选定）

- 终态 `turn/end` 增加 `error_type`（类别）；`reason_text` 承载异常链文本（最多 3 层）。
- `llm/retry` 记录增加 `error_type` + `error_message`，并把 append 从"只在决定重试时"扩展到覆盖 `dont_retry` 与"重试耗尽"两个收尾出口（`decision: retry / give_up`）。

**优势**

- 每次失败同构：N 次重试 + 1 次终止共 N+1 条记录，条数与实际失败次数一致。
- 决定任务终止的那次也可结构化查询。
- 只有一种记录语义，无特例分支。

**劣势**

- 同一错误出现两次：`llm/retry` 一条结构化记录 + `turn/end` 链中一句文本（约百字节冗余）。
- `llm/retry` 的语义从"重试决定"扩大为"失败处置记录"。

### 方案 B：终态同上，但重试收尾不落记录

`llm/retry` 只记"决定重试"；收尾错误仅存在于 `turn/end` 的 `reason_text` 文本中。

**优势**：少一条记录；`llm/retry` 语义保持"只表示发生过重试"。

**劣势**：N+1 次失败中最后一次只有文本形态，与其它次不同构，容易误读为"只失败 N 次"；决定终止的那次恰是最该看清的，却最弱；若最后一次错误类型与前几次不同，其 `details` 无从查起。

### 方案 C：把异常链结构化嵌套进终态记录（否决）

终态记录直接承载 `cause` 的嵌套结构。

**劣势**：与前提 6、10 冲突——没有需要嵌套的根因层级，也没有按根因聚合的需求；schema 变成递归结构，消费方（评估脚本、统计）成本上升；稳定性差。

### 方案 D：只记 str（现状，否决）

**劣势**：违反前提 1，正是本决策要解决的问题。

## 决策逻辑

| 前提条件 | 对应决策 | 前提失效时的切换 |
|----------|----------|------------------|
| 前提 1 + 2：session 是唯一日志，且终态只有字符串字段 | 必须把"类别 + 根因"写进 session | — |
| 前提 3：错误链最长 3 层 | 链**限深 3 层** | 出现更长链 → 截断处显式标记（如 `…(还有 N 层)`）；注意截断从外往内，丢的是最内层 |
| 前提 4：错误包装只用显式 `raise ... from e` | 只沿 `__cause__` 遍历，不接 `__context__` | 出现隐式包装 → 需兼容 `__context__` |
| 前提 5：`ExceptionGroup` 不在链上 | 链遍历须对 group 特判并展开 `.exceptions` | 出现其它"容器型"错误载体 → 需扩展对应展开逻辑 |
| 前提 6 + 7 + 8：只有 LLM 重试是多层，且它已有独立通道、工具失败另走 `tool/result` | 终态只记"类别 + 摘要"，根因交给 `llm/retry` 发生点，**不做嵌套追踪** | 出现新的多层错误 → 重新评估终态是否需跟踪下层 |
| 前提 9：每次重试的错误可能不同 | 每次失败都落一条记录（**方案 A**，非 B） | 错误实际恒定、且不在意终止那次的结构化查询 → 可退回方案 B |
| 前提 10：无"按根因聚合统计"的需求 | 链用**文本**而非结构化嵌套（否决方案 C） | 出现按 cause 聚合的需求 → 重新评估方案 C 的 schema 成本 |

## 演进历史

| 版本 | 方案 | 解决的问题 | 引入的新问题 |
| ---- | ---- | ---------- | ------------ |
| v1 | 终态只记 `str(异常)` | 最省事 | 只看 session 无法判断类别、无法回溯根因 |
| v2 | 终态记「类别 + 异常链」；`llm/retry` 仅记"决定重试" | 终态可读、重试次数可见 | 最后一次失败只有文本形态，与其它次不同构；其 details 丢失 |
| v3 | 重试的每次失败都落记录（含收尾）（最终） | 每次失败同构、终止那次可查询 | 同一错误在 session 中出现两次（记录 + 终态链） |

## 最终决策

当前成立的前提：前提 1~10。

因此选择 `方案 A`：

- `turn/end` 携带 `error_type`（类别）；`reason_text` 承载异常链文本，最多 3 层，超出则显式标记截断。
- 异常链遍历规则：沿 `__cause__` 逐层输出 `类型: 消息`；遇到 `BaseExceptionGroup` 则展开其 `.exceptions`（group 不在链上）。本仓库的错误包装均为显式 `raise ... from e`，故只走 `__cause__` 即可，无需接 `__context__`。
- `llm/retry` 增加 `error_type` + `error_message`，并在三个出口（决定重试 / 决定不重试 / 重试耗尽）都落一条，以 `decision` 区分 `retry` 与 `give_up`。
- `step/end` 不新增 `error_type`。

前提失效时的切换路径：见决策逻辑表。

## 决策原因

- 原因 1：前提 1 + 2 下，判据是"只读 session 就能定位错误"。只记 str 时同一条错误可能呈现为底层库裸文本或被包装的摘要，类别与根因双双丢失（现状）。
- 原因 2：前提 6 + 7 + 8 下，唯一多层错误只有 LLM 重试，而它有独立的 `llm/retry` 可在发生点承载原始信息。终态只需"类别 + 摘要"，把根因留给发生点，故不做嵌套追踪。
- 原因 3：前提 10 下，异常链用文本而非结构化嵌套（对比方案 C）——文本满足"人快速定位"，结构化会引入递归 schema 与消费成本，而"按根因聚合统计"当前不是需求。
- 原因 4：前提 9 下，A 与 B 的唯一实质差别是"最后一次失败是一条记录还是一句文本"。若错误每次可能不同，B 的同构性被破坏、条数也不准；而 A 的代价仅是一处百余字节的重复，且该重复与已接受的 `step/end` 与 `turn/end` 冗余同性质。
- 原因 5：前提 7 下，重试次数与错误原文都应可结构化查询——这正是 `llm/retry` 存在的意义，把发生点信息放在它上面比在终态重复展开更省。

## 后续影响

- `LLMRetryData` 需增加 `error_type` / `error_message` 字段；`TurnEndData` 需增加 `error_type` 字段。
- 需要提供一个异常链格式化函数（沿 `__cause__` 遍历、限深 3、展开 `ExceptionGroup`、处理长度与敏感信息）。
- `llm/retry` 的语义正式扩展为"一次失败的处置记录"；后续读取方（评估、统计）不应假设它只表示"发生过重试"。
- 错误类别的枚举清单与命名尚未定义，落地前需补齐（本 ADR 只定形态）。**部分已明确**：见 2026-09-15《异常分类树新增策略域与未知域》——新增 `AgentPolicyError`（步数上限、重试上限）与 `AgentUnknownError`（归因失败兜底）。
- 待验证：3 层上限在新增包装层后是否仍够用；截断标记能否被消费方正确识别。
