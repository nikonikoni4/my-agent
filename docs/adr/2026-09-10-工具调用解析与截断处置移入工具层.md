# 工具调用参数解析与截断处置移入工具层

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿（取代 2026-09-09-工具调用截断与JSON解析错误分类.md） |

## 问题界定

### 问题简述

工具调用 arguments 的 JSON 解析失败（普通非法 JSON 与 max_tokens 截断）原先由 provider 抛 `LLMToolCallParseError` / `LLMToolCallTruncatedError`，进入 LLM 调用错误路径（request/error + 重试策略注册表）。但这类失败发生在**模型输出完成之后**：usage 已返回、finish_reason 已确定，把它归入"调用错误"与分类树的来源轴错位；且异常在 LLMResponse 产生之前抛出，模型的错误输出既不进对话也不进 trace，重试又是无新信息的原样重发——既无法给模型 hint 自纠，也丢掉了纠错所需的现场。

### 讨论范围

- 解析职责的归属层（provider / 工具层 / loop）。
- `RawToolCall` 的 arguments 类型契约（wire 原样字符串 vs 解析后的 dict）。
- 截断重要性的表达载体（异常类型 vs finish 信息链路）。
- 解析失败的熔断计数语义。

### 非讨论范围

- request/error waterfall 的接线与重试动作实现（独立的在途决策）。
- 熔断阈值数值与三种熔断模式的选择（既有决策，见 架构设计/工具调用.md）。
- 错误路径补 finish 块的具体实现（方向已定，后续任务，见后续影响）。
- 上下文超长（LLMContextExceededError）等真正的调用期错误。

### 模糊信息的明确定义

- **解析失败（Parse）**：`json.loads` 抛 JSONDecodeError，结构语法错误，与输出长度无关。
- **截断（Truncated）**：`finish_reason == "length"`，参数本可合法但生成中途被 max_tokens 切断。

（定义沿用被取代 ADR。）

### 问题深度

信任边界的位置与错误分类轴的架构原则问题：什么算"调用错误"、模型输出不可信由谁判定、响应级信息如何下沉为调用级语境。

## 现状（决策时）

- 旧 ADR 已实施：provider 的 `parse_tool_call` / `check_truncated_tool_calls` 抛两个异常，平铺并列于 `LLMCallError` 下；llm_retry 策略注册表把解析失败登记为"马上重试"（同一消息列表原样重发，无新信息）。
- 工具层已有成熟的 hint 回喂机制：参数校验失败返回 `ToolResult.error`（错误信息 + hint），以 `role="tool"` 消息回喂，模型下一轮自纠，且不中断 ReAct 循环。
- request/error 的 waterfall 接线与重试动作均未落地（独立在途决策）。

## 决策前提

- 前提 1（发生阶段）：解析失败发生在模型输出完成之后——usage、finish_reason 均已返回，结果已经输出了。它不是"调用"失败：`LLMCallError` 的定义是 SDK 异常的翻译，而解析失败处理的是正常返回值。
- 前提 2（回喂通路）：工具层已有 hint 回喂机制（`ToolResult.error` → `role="tool"` 消息 → 模型自纠），解析失败天然复用该通路；异常路径无法携带 hint。
- 前提 3（调用错误的对照处置）：LLM 调用过程中出错（**不含"取消"**——取消单独处理、不走 request/error）时不补 assistant 消息——流中断时没有完整回复可落盘。chunk 体系已新增 **finish 块**（`StreamChunk.finish_reason`，仅流正常结束时产出，中途出错自然缺失，以此区分正常结束与中断）；LLM 调用错误处理中应补 finish 块标记异常结束（已定方向，未实施）。
- 前提 4（截断强调的载体）：旧 ADR 以"独立异常类型平铺并列"表达截断的重要性；该强调改由 finish 信息链路承载——finish_reason（finish 块携带）→ provider 给 `RawToolCall` 打 `truncated` 标记 → 工具层选择截断专属回喂话术。
- 前提 5（熔断语义，用户判断）：熔断的目的是**避免模型反复调用一个工具一直出错**——既包括模型出错（参数写坏）也包括工具出错（执行失败），两类失败同等计数。

## 可选方案

### 方案 A：解析与截断处置移入工具层（选定）

`RawToolCall.arguments` 保持 wire 原样 JSON 字符串（provider 纯翻译，不解析不校验）；`ToolRegister.parse_call` 在信任边界完成 json.loads + dict 校验，失败返回带 hint 的 `ToolResult`（原文 + 错误位置回显）回喂模型；截断由 provider 依据 finish_reason 打 `truncated` 标记、工具层据此选话术；解析失败计入熔断。`LLMToolCallParseError` / `LLMToolCallTruncatedError` 从分类树删除。

**优势**

- 错误分类轴归位：输出后处理不再是"调用错误"。
- 模型的错误输出保留在对话与 trace 中（assistant 带 tool_calls 落盘 + tool 结果回喂），一轮多对话即可自纠，而非无信息重发。
- DTO 单一类型（arguments 恒为 str），无 union。
- loop 纯编排，不染指领域话术。

**劣势**

- 模型侧的参数失败会消耗健康工具的熔断额度（阈值内依赖模型自纠恢复计数清零）。
- provider 与工具层之间多一个契约字段（`truncated`）需要维护语义。

### 方案 B：保留 provider 异常 + raw_arguments 透传（否决）

解析仍在 provider，失败时把原始串放进异常 details / DTO 附加字段交上层回喂。

**优势**

- provider 保留"见到坏 JSON 立即报告"的位置。

**劣势**

- DTO 出现 dict | str union，契约污染。
- 分类轴仍错位；回喂逻辑被拆到 loop。

### 方案 C：解析移入工具层，截断话术放 loop（否决，曾实施一版）

解析在工具层，但 loop 依据 `response.finish_reason` + `is_parse_error` 给解析失败的结果补截断话术。

**优势**

- 工具层不需要额外信息。

**劣势**

- loop 是纯编排层，不应懂"截断 vs 语法错误"的领域话术。
- finish_reason 是响应级信息，应由拥有它的 provider 翻译成调用级标记，而不是由 loop 消费。

## 决策逻辑

| 前提条件 | 对应方案 | 备注 |
|----------|----------|------|
| 前提 1 + 2 成立（输出已完成 + 已有回喂通路） | 方案 A | 当前选择 |
| 前提 4 失效（finish 信息链路不足以表达截断重要性） | 在 request/error 侧为截断恢复增加人工介入挂点 | 备选触发 |

## 最终决策

当前成立的前提：前提 1—5。

因此选择**方案 A**：解析与截断处置移入工具层，`LLMToolCallParseError` / `LLMToolCallTruncatedError` 从分类树删除，截断强调由 finish 信息链路（finish 块 → truncated 标记 → 专属话术）承载。

前提失效时的切换路径：见决策逻辑表。

## 决策原因

- 原因 1（对应前提 1）：解析失败与 LLM 请求错误无关——**结果已经输出了**；按"错误来源/发生阶段"分类的树上它不占 `LLMCallError` 的位置。
- 原因 2（对应前提 2）：工具调用中可以给 hint 提示，模型下一轮自纠；异常路径切断了这条通路。
- 原因 3（对应前提 3）：真正的 LLM 调用错误（不含取消）不补 assistant 消息，由 chunk 体系新增的 finish 块区分正常结束与中断，错误处理中应补 finish 块——解析失败不属于这条路径。
- 原因 4（对应前提 4）：被取代 ADR 中"以独立错误类型强调 max_token 截断"的强调，**现在被移动到 finish 块中了**——finish_reason 经 finish 块显式落到 session，再经 truncated 标记驱动截断专属话术，重要性不再需要异常类型身份来表达。

## 后续影响

- **代码结构**：`ToolCallRequest` 更名 `RawToolCall` 且 `arguments: str`（wire 原样）；工具层新增 `ParsedToolCall` 与 `ToolRegister.parse_call`；`ToolResult` 新增 `is_parse_error`；provider 的 `parse_tool_call`/`check_truncated_tool_calls` 删除，chat/stream 均为纯提取；`execption.py` 删除两个异常类型；llm_retry 注册表 `retry_type` 清空。
- **数据**：`ToolCallData.arguments` 记 wire 原样 JSON 字符串（忠实记录模型输出）；store 还原兼容旧格式（落盘为 dict 时序列化回字符串）。
- **话术**：截断（精简参数 / 拆分调用）与语法错误（对照错误位置修正）两类 hint 由 `parse_call` 依据 `truncated` 分流；被取代 ADR 的截断三成因治理建议（调 max_tokens 配置 / 减少单次体量 / 提示词前置约束）沉淀在截断话术中。
- **熔断**：解析失败与执行失败同等计数，连续达到阈值同样触发 schema_hide / execute_intercept / raise_on_break；turn/end 清零的既有语义不变。
- **后续任务**：LLM 调用错误（不含取消）处理中补 finish 块（`openai_provider.stream_chat` 尾部注释已标注）；request/error waterfall 接线与重试动作（独立在途决策）；hint 自纠率与熔断误伤的观测。
- **测试**：解析失败回喂（不执行工具、计入熔断）、连续解析失败触发熔断、截断/语法话术分流、provider 打 truncated 标记、e2e 真实链路（session 落盘还原含 RawToolCall 往返）。
- **文档**：2026-09-09-工具调用截断与JSON解析错误分类.md 状态改为 superseded；其"截断与解析必须分开处置"的内核以 truncated 标记 + 分流话术的形式保留。
