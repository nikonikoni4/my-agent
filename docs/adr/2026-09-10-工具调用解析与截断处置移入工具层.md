# 工具调用参数解析与截断处置移入工具层

> **v2.0 说明**：标题中的"解析移入工具层"自 v2.0 起只对**解析失败后的处置**成立——解析动作本身已回到 provider 尽力完成。标题沿用以免断链，最新约定以本文正文为准。

## 版本

| 版本 | 更新内容 |
| ---- | -------- |

| 2.0 | provider 改为**尽力解析** arguments（仅当 json.loads 结果是 JSON 对象时换为 dict，其余保持原字符串）；DTO 契约由 `arguments: str` 改为 `str \| dict`；工具层保留解析失败的处置与熔断；「最终决策」改为编号列表并逐条附用户原话 |
| 2.1 | tool/call 的 payload 由逐条（`tool_name` / `tool_params`）改为整批 `tool_call_requests`，护栏逐条判定、只读不改输入（决策 6、7）；session 的 `ToolCallData.arguments` 由恒为字符串改为按拿到时的形态落盘（`str \| dict`），报表侧在读回边界归一化 |

## 问题界定

### 问题简述

v1.0 确立了"解析失败（普通非法 JSON 与 max_tokens 截断）不作为 LLM 调用错误、由工具层以带 hint 的 ToolResult 回喂"这条内核，并由此把解析动作整体收进工具层信任边界，provider 退为纯翻译。

但这带来一个落地问题：**游走于"模型发起调用"与"工具执行"之间的组件（如 pre-tool-use 护栏）拿不到结构化参数**——它要么自己重新 `json.loads`（出现第二个信任边界），要么放弃参数只看到一段未经解析的字符串。而 DTO 契约（`arguments: str`）又把"已经解析好的结果"挡在了传输路径之外。

本次要定的是：**解析动作能否在 provider 顺手做掉，同时不破坏"失败处置在工具层"这条内核。**

### 讨论范围

- 解析动作的归属：只在工具层，还是 provider 也做一次。
- 解析结果的表达：另设标志位字段，还是靠类型本身区分。
- DTO 契约：`arguments` 保持单一 `str`，还是允许 `str | dict`。
- 未解析成功的调用，下游（护栏）如何对待。

### 非讨论范围

- 解析失败的话术、熔断计数、回喂通路（v1.0 已定，本次不改）。
- 截断的识别与话术分流（`truncated` 标记链路，v1.0 已定，本次不改）。
- 护栏/熔断等治理逻辑的归属与挂点（独立的在途决策）。

### 模糊信息的明确定义

- **解析成功**：`json.loads` 不抛错，**且结果是 JSON 对象**（`dict`）。只有这一种情况被视作"解析出来"。
- **解析失败**：`json.loads` 抛 JSONDecodeError（非法 JSON），或结果不是对象（数组 / 数字 / null 等）。
- **截断（Truncated）**：`finish_reason == "length"`，参数本可合法但生成中途被 max_tokens 切断。

（定义沿用 v1.0，本次补入"结果非对象"归入解析失败。）

### 问题深度

信任边界的位置与 DTO 契约的形状：解析作为一次无副作用的纯数据形态转换，能否前移到翻译层；失败判定与处置是否必须与解析动作绑定在同一层。

## 现状（v2.0 决策时）

- v1.0 已实施：`RawToolCall.arguments: str` 恒为 wire 原样 JSON 字符串；`ToolRegister.parse_call` 完成 `json.loads` + dict 校验，失败返回带 hint 的 `ToolResult`（原文 + 错误位置），计入熔断；`LLMToolCallParseError` / `LLMToolCallTruncatedError` 已从分类树删除。
- `ToolCallPayload` 当时声明的是 `tool_name: str` / `tool_params: dict` 两个字段（逐条，占位），尚未被填充——护栏这一侧对结构化参数的诉求已经写进契约。（v2.1 起该契约改为整批 `tool_call_requests: list[ToolCallInfo]`，见「最终决策」决策 6；本节其余内容描述的是 v2.0 决策时的状态。）
- 工具层已有成熟的 hint 回喂机制与熔断计数，v1.0 的失败处置通路可原样复用。
- pre-tool-use 护栏尚未落地（在途）。

## 决策前提

- 前提 1（解析无副作用）：`json.loads` 是纯数据形态转换，不产生领域判断，放在哪一层都不改变"模型输出不可信"这一事实本身。
- 前提 2（失败处置不能跟着走）：失败之后的话术分流、熔断计数、回喂通路是本仓库的领域语义，必须留在工具层——这是 v1.0 的内核，本次不动。
- 前提 3（中间消费者的诉求）：护栏等组件在"模型发起调用"与"工具执行"之间工作，需要结构化参数；若拿不到，就会长出第二个解析点。
- 前提 4（类型可承载状态）：解析失败时保留原字符串，即可用类型本身区分"已解析 / 未解析"，无需另设标志位字段。
- 前提 5（wire 契约要求字符串）：回发给供应商的 `arguments` 必须是 JSON 字符串（`to_dict`），session 记录同样取字符串形态。

## 可选方案

### 方案 A：provider 尽力解析，工具层保留处置（选定）

provider 在提取 tool_calls 时尝试 `json.loads`，**仅当结果是 JSON 对象**才把 `arguments` 换成 dict；其余一律保持原字符串。`RawToolCall.arguments` 类型为 `str | dict`，**凭类型区分，不设标志位**。工具层 `parse_call` 遇到 str 走原有解析与回喂，遇到 dict 直接使用；`truncated` 标记链路与熔断语义不变。

**优势**

- 中间消费者（护栏）直接拿到 dict，不产生第二个解析点。
- 失败处置、熔断、话术全部留在工具层，v1.0 的内核完整保留。
- 无额外字段：类型即状态。

**劣势**

- DTO 由单一类型变为 `str | dict`，消费方需按类型分流。
- 解析成功时模型当时写的文本不再保留（`to_dict` / session 记录取序列化后的等价 JSON）。
- provider 从"纯翻译"变为"翻译 + 尽力解析"，其职责定义被改写。

### 方案 B：另设标志位字段（parsed / parse_ok）（否决）

`arguments` 保持 `str`，追加一个布尔或派生字段表示是否已解析。

**否决理由**

- 同一份数据的两种形态并存，且标志位与内容可能不同步；类型本身已经足够表达，多一个字段是冗余状态。

### 方案 C：解析整体留在工具层，护栏自行解析（否决）

维持 v1.0，中间消费者各自 `json.loads`。

**否决理由**

- 出现第二个信任边界，解析规则与失败判定会在多处漂移；这正是本次要消除的问题。

### 方案 D：`arguments` 保持恒为 `str`，provider 另填旁路字段（否决）

raw 原文不动，另加 `parsed_arguments: dict | None`。

**否决理由**

- 引入"原文 + 其解释"两份并存的数据，消费方需要判断以哪个为准；用户已选择用类型区分（见「最终决策」决策 2）。

## 最终决策

- 决策 1：`arguments` 的解析在 provider（LLM 侧）做一次；出错时不报错、不抛异常，等进入工具执行时再由工具层报错。
  - 依据（用户原话）：「RawToolCall 的  arguments 还是正常解析，再llm里面，然后出错了不报错，等进入tool执行在等他抛出」

- 决策 2：已解析与未解析两种形态**凭类型区分，不另设标志位**——是 `str` 就由工具内部校验，不是就直接拿去走下一步。
  - 依据（用户原话）：「如果argment 是 str 工具内部就校验，不是则跳过这个直接拿argment进行下一步」

- 决策 3：解析失败（没解析出来）的调用，上游不处理、直接跳过。
  - 依据（用户原话）：「这样在waterfall内容如果没有解析出来，就不管了（虽然说从优先级上来说应该是权限先，但是这里解析不出来也没有办法）」

- 决策 4：解析失败仍由工具层处置，**不作为 LLM 调用错误**（v1.0 内核保留）。
  - 依据（用户原话）：「出现错误不报错等待工具内报错」

- 决策 5：本次**不是否决** 2026-09-10（v1.0）的 ADR，而是对它的局部修订（补一处解析）。
  - 依据（用户原话）：「当前并不是否决之前的adr，而是补充一处校验，实际算起来改动的地方也就只有一处llm内部增加一个校验」

- 决策 6：`tool/call` 的 payload 携带**整批**工具调用（`tool_call_requests`）——其他订阅方要看到全部调用才能判断；护栏自身仍是逐条判断。
  - 依据（用户原话）：「我把输入改为tool_call_requests，类型是list[RawToolCall]，这里是因为可能别的 waterfall需要全部的调用信息而不是一个一个进行判断。但是在这里只需要一个一个判断」

- 决策 7：护栏不得修改输入的原参数内容。
  - 依据（用户原话）：「不能修改输入的原参数内容」

## 已接受的实现选择（非用户决策）

以下为实现方在落地时自行做出的选择（含为闭合契约漏洞所做的调整），**用户尚未以原话表态**，不作为决策：

1. **只有解析结果是 JSON 对象才替换为 dict**：`json.loads("[1,2]")` 得到 list、`json.loads("123")` 得到 int、`json.loads("null")` 得到 None，这些既不是 str 也不是 dict。若原样替换，决策 2 的分流（"不是 str 就直接拿去执行"）会把它们送进执行路径、绕过 `PARSE_NOT_OBJECT` 的回喂，最终在参数校验处炸成工具内部错误。故把"解析成功"收窄为"结果是对象"，使"非 str 必然是 dict"成立。
2. **`to_dict()` / session 记录序列化 dict 时使用 `ensure_ascii=False`**：该方法每次请求都会执行（历史 assistant 消息连同 tool_calls 回放给供应商），默认的 `ensure_ascii=True` 会把中文转义成 `\uXXXX`，参数含中文时体积与 token 成倍增长。
3. **新增 `RawToolCall.raw_arguments` 属性**：str 原样返回、dict 序列化回去，`to_dict()`、`ToolResultPayload.arguments` 两处取值统一走它（两处契约都要求字符串）。写入时 `ToolCallData.arguments` 也走过它，但 v2.1 起该处改为直接取 `tool_call.arguments`（见下方第 7 条）。
4. **截断（`truncated`）时不做特殊处理**：仍尝试解析，失败即保持原字符串，由工具层按既有分流给截断话术。
5. **payload 里的调用由 infra 自定义的 `ToolCallInfo` 承载，而不是直接把 `RawToolCall` 放进 payload**：决策 6 的用户原话里类型是 `list[RawToolCall]`；落地时改为同形但定义在 `infra/events/payload.py` 的小 DTO，因为 `payload` 至今只依赖原语，直接引入 `RawToolCall` 会让 `infra` 反向依赖 `agent.core`（不是循环 import，能跑，但方向是反的）。
6. **护栏裁决值的形状与是否截断链**：用户原话的形状是 `list[call_id:{decision:... reason}]`，落地为 `dict[call_id, {"decision": "deny", "reason": str}]`，且**只装反对意见**（缺席 = 不反对）；有反对意见时也照常 `await _next()`，把下游的反对并进来（不截断链，否则护栏反对 call A 会连带让 B 免检）。形状与截断与否这两点由工具询问的选项确定，按 adr-write-rules §2.3 不构成用户表态。
7. **`ToolCallData.arguments` 落盘保留两种形态，归一化放在各读回侧**：落盘按拿到时的形态原样存（provider 解析成功是嵌套对象、未解析成功是 wire 原文），报表侧在 `stats/session_view.py` 的读回边界统一成字符串。用户对该改动只做过影响面的询问，实施指示为「这个直接修改一下就行」——指向的是报表侧怎么改，未对落盘形态本身表态。

## 未决项（待用户确认，非决策）

- 本文标题与文件名"解析与截断处置移入工具层"在 v2.0 后已不能完整描述内容（解析动作已回到 provider）。是否改名并同步 `index.md` 与 2026-09-09 ADR 中的链接，尚未确认。

## 决策原因

- 原因 1（对应决策 1、5）：解析是纯数据形态转换，无副作用、不含领域判断；把它顺手做掉不改变信任边界，只让下游少做一次重复劳动（对应前提 1）。
- 原因 2（对应决策 2）：`str` 与 `dict` 已经构成完备的二态划分，单独加一个标志位会引入与内容可能不同步的冗余状态（对应前提 4）。
- 原因 3（对应决策 4）：失败仍在工具层——话术、熔断计数、回喂通路都是本仓库的领域语义，且"结果已经输出了"这一分类轴判断未变（对应前提 2）。
- 原因 4（对应决策 3）：解析失败的调用本就走不通执行路径，护栏跳过它不产生"绕过护栏执行危险动作"的口子；护栏只处理已成形的动作。

## 后续影响

- **代码结构**：`RawToolCall.arguments` 改为 `str | dict` 并新增 `raw_arguments` 属性；`extract_tool_calls` 增加尽力解析；`ToolRegister.parse_call` 增加 dict 直通分支；`to_dict()` 改为经 `raw_arguments` 取值；`TOOL_RESULT` payload 仍取 `raw_arguments`（该 DTO 的 `arguments` 契约仍是字符串，见 `payload.ToolResultPayload`）。v2.1 起：`ToolCallPayload` 携带 `tool_call_requests: list[ToolCallInfo]`；loop 写 `tool/call` 记录改取 `tool_call.arguments`（不再经 `raw_arguments` 序列化）。
- **数据**：session 的 `ToolCallData.arguments` 为 `str | dict`——解析成功落盘为嵌套对象，未解析成功落盘为模型原文。v2.0 时是"恒为字符串"（解析成功时是序列化后的等价 JSON），v2.1 起改为按拿到时的形态原样存；读回侧各自决定要哪种形态（报表侧见 `stats/session_view._wire_arguments`）。
