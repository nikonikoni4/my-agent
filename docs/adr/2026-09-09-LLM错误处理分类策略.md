# LLM 错误处理分类策略

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿（方向：内部翻译 + 单点捕获 + 异常分类树） |
| 1.1 | 明确分类树形状：按错误来源分类；重试策略从类型上剥离，放入独立策略注册表 |

## 问题界定

### 问题简述

LLM 调用会抛出一族具体差异很大的错误（认证失败、限流、连接断开、上下文超长、内容审核、截断等），它们的恢复策略完全不同。决策主要问题：这些错误应该在哪里被识别和分类——是在 **LLM 层内部**先收集、翻译成统一业务异常再抛出，让 agent 内核只做一次捕获；还是 **让原始错误全部抛到 loop**，由 loop 分别捕获再处理。

### 讨论范围

- LLM 层（provider）对 SDK 原始异常（openai.APIError 家族）的处理方式。
- agent 内核（`ReActAgentLoop.step`）对 LLM 错误做单点捕获的归属。
- 错误分类的表达形态：异常分类树 + 恢复策略（重试/降级/人工介入）挂类型。

### 非讨论范围

- 具体的异常子类清单（RateLimit/Auth/Connection/ContextExceeded…）——用户明确留待后续独立设计，本 ADR 只定"分类树"这一形态。
- `request/error` 事件的职责边界——用户明确本次不记录，留待后续决策。
- 具体重试次数、退避算法、降级文案等实现细节。
- 工具执行错误（Tool 层）的处理——不属于本次 LLM 错误范围。

### 模糊信息的明确定义

- **领域异常 / 业务异常**：指 `MyAgentError` 子类，是 agent 各模块自身定义的异常，与具体 SDK（openai）无关。
- **原始错误**：指 SDK 直接抛出的异常（`openai.APIError` 及其子类），或基础库异常（如超时）。

### 问题深度

涉及错误如何穿越分层边界（LLM 层 → agent 内核层）、agent 内核的捕获结构，以及"错误策略放哪判定"的架构原则问题，属于长期维护方式决策。

## 现状

- `openai_provider.py` 已把 `openai.APIError` 翻译为 `LLMCallError` 抛出（`chat` 与 `stream_chat` 均有）。
- `execption.py` 已落地来源分类树：`LLMCallError` 为基类，子类按来源分组——配置类（`LLMAuthError`/`LLMModelError`/`LLMEndpointError`）、限流配额类（`LLMRateLimitError`/`LLMQuotaError`）、连接类（`LLMConnectionError`）、请求内容类（`LLMContextExceededError`/`LLMToolCallTruncatedError`）。未识别来源回落到基类。
- 当前 `loop.step` 只捕获 `TimeoutError` 与 `asyncio.CancelledError`，未捕获 `LLMCallError`，因此 LLM 领域错误会沿 `step → turn` 一路冒泡到最外层，缺少统一的单点处理点。
- 重试策略注册表尚未实现（它是 loop 侧逻辑，当前决策已定其形态，落地为后续任务）。

## 决策前提

- 前提 1（用户决策）：LLM 错误应在 LLM 层内部收集、分类、转化为业务异常后再抛出，不让 SDK 原始异常漏到 agent 内核层。
- 前提 2（用户决策）：agent 内核只需针对领域异常做**单点捕获**，避免在 loop 里分散捕获各种原始错误。
- 前提 3（用户约束/现状）：所有 LLM 错误的处理最终会集中在一处进行。若分散捕获，则那处处理器内部仍需重新整合并判断各种原始错误，属于重复工作。
- 前提 4（用户约束）：分散捕获会让 loop 内代码变乱。
- 前提 5（用户决策，1.1 修正）：错误分类用**异常分类树**表达，分类主轴是"错误来源"（配置/限流配额/连接/请求内容等），基类 + 按来源拆的子类。
- 前提 6（用户决策，1.1 新增）：重试策略**不与异常类型绑定**，而是放独立的策略注册表（异常类型 → 策略），避免"改策略要动类型树"。分类用来源保证稳定；策略用注册表保证易变易改。
- 前提 7（用户约束）：本 ADR 只记录"方向 + 分类树策略"；具体来源子类清单后续按需补充（现有子类已落 execption.py，发现新来源再添）。

## 可选方案

### 方案 A：内部翻译 + 单点捕获 + 异常分类树（方向，选定）

LLM 层把 SDK 原始异常分类翻译成领域异常后抛出；agent 内核只需要一个针对基类（如 `LLMCallError`）的捕获点；无需查看原始异常、无需剥 `__cause__`。

**优势**

- 错误处理集中在一处，避免分散捕获导致的重复整合判断。
- SDK 类型不污染 agent 内核层，分层干净。
- 扩展时只在 LLM 层加子类，内核无需改动。

**劣势**

- 需要在 LLM 层维护一套映射（SDK 异常 → 领域子类）。
- 分类粒度不当会有额外维护成本（见决策逻辑防御性调整行）。

### 方案 A 内部的形状候选（本次 v1.1 的分枝）

方向「分类树」确定后，还差一个形状问题：分类主轴用什么维度。

**A1 处理角度：按恢复动作分类（曾考虑，否决）**

按"马上重试 / 延迟重试 / 不重试"分三类，把重试策略直接体现在类型里。

- 优势：loop 判重试只看类型，与"loop 决策"消费者一拍即合。
- 劣势：**策略是易变信息**（常因新发现某错误其实可重试而调整），焊死在类型树上后，"改策略"变成"挪树"，结构和迁移成本高。且监控若想按"重试动作"聚合，也依赖类型而非独立维度。

**A2 来源角度：按错误来源分类 + 独立策略注册表（选定）**

按来源分类（配置 / 限流配额 / 连接 / 请求内容…），重试策略剥离开，放入独立的策略注册表（异常类型 → 策略）映射，未登记时走默认策略兜底。

- 优势：来源稳定、语义明确、几乎不变；重试策略易变。二者解耦后，**"发现某错误其实可重试"只改注册表那一行，异常树一个类都不用动**。loop 仍是单点捕获：`except LLMCallError:` 查注册表得 `action`（马上/延迟/不重试）再分支；监控按查出的 action 聚合，不依赖类型。
- 劣势：多维护一张注册表；来源未覆盖时靠基类兜底（可接受）。

### 方案 B：原始错误全部抛到 loop 内分散捕获

不预先分类，SDK 原始异常直接冒泡到 loop，分别捕获处理。

**优势**：LLM 层不用维护映射，少一层翻译代码。

**劣势**：agent 内核直接依赖 SDK 类型，分层被破坏、换供应商要改内核；错误处理分散，最终仍需归集判断原始错误（违反前提 3）；loop 变乱（前提 4）。

## 决策逻辑

| 前提条件 | 对应方案 | 备注 |
|----------|----------|------|
| 前提 1 + 2 + 3 + 4 + 5 成立（当前状态） | 方案 A | 方向：当前选择 |
| 前提 5 + 6 成立（来源分类 + 策略独立） | 方案 A2 | 形状：当前选择 |
| 需要凭类型直接判重试、且接受改策略动树 | 方案 A1 | 备选触发条件 |
| 某类错误需要类型化无法承载的个性化恢复流程 | 方案 A，该特例在 loop 内单独处理，仍复用领域异常包装 | 备选触发条件 |
| 出现"分类树无限细分导致维护成本 > 收益"的实证 | 收敛子类数量（来源维持稳定，不为策略扩张命名） | 防御性调整 |

## 演进历史

| 版本 | 方案 | 解决的问题 | 引入的新问题 |
| ---- | ---- | ---------- | ------------ |
| v1 | 统一为单个 `LLMCallError` | 先把 SDK 异常翻译成领域异常 | 单一异常无法表达恢复策略，仍要剥 `__cause__` |
| v2 | 异常分类树，策略挂类型（曾倾向） | 单点处理器靠类型分支 | 策略绑死类型，改策略得挪树 |
| v3 | 来源角度的分类树 + 独立策略注册表（最终） | 来源稳定、策略易变二者解耦；改策略只改映射 | 多维护一张注册表；来源未覆盖靠基类兜底 |

## 最终决策

当前成立的前提：前提 1、2、3、4、5、6、7。

因此选择 `方案 A`（方向）+ `方案 A2`（形状）：LLM 层内部把原始错误按**来源**翻译成领域异常分类树，agent 内核单点捕获，重试策略放在独立的策略注册表（异常类型 → 策略）而非异常类型上。现有来源子类已落 execption.py；发现新来源时在 llm 层补子类，调整策略时只改注册表。

前提失效时的切换路径：见决策逻辑表。若要凭类型直接判重试且接受改策略动树，切 A1；某类需个性化流程时在 loop 单独处理（仍包领域异常）；分类树过度细分时收敛子类。

## 决策原因

- 原因 1：所有 LLM 错误处理最终集中在同一处（前提 3），LLM 层统一翻译避免"分散捕获后再归集判断原始错误"的重复工作。
- 原因 2：不让 SDK 类型进入 agent 内核层（前提 1、2），换供应商不波及内核。
- 原因 3：分类主轴选"来源"而非"恢复动作"（前提 5 + 6）——来源稳定几乎不变、重试策略易变，把易变信息从类型树中剥离到策略注册表，使"改策略不挪树"成为可能；否则策略焊死在类型上，正是想避免的高迁移成本。

## 后续影响

- 后续任务（独立设计，不在本 ADR）：`loop.step` 补一个针对 `LLMCallError` 的单点捕获分支（当前未捕获，会一路冒泡）；实现重试策略注册表（异常类型 → 策略，含次数/退避/是否改请求）；`request/error` 事件上报内容。
- 后续任务：`openai_provider` 的翻译映射目前仍统一抛 `LLMCallError` 基类，未按来源细分（401→Auth、404→Model、429→RateLimit 等），需按来源翻译到具体子类。
- 现有来源子类（含 `LLMToolCallTruncatedError`）已是分类树一部分；发现新来源时在 execption.py 按当前结构补充。
- 实现时注意分类树的粒度（见决策逻辑防御性调整行）。
