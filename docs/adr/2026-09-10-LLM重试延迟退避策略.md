# LLM 重试延迟退避策略

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建初稿：统一指数退避公式；retry 与 backoff_retry 仅基准值不同；参数放策略注册表；有 Retry-After 时优先采用 |

## 问题界定

### 问题简述

`loop.step` 在捕获 LLM 错误、经 `request/error` 拿到策略决策（`retry` / `backoff_retry` / `dont_retry`）后，重试前需要等待一段时间。决策问题：**这段等待时间怎么算、参数放哪、与服务端建议的 Retry-After 如何取舍**。

### 讨论范围

- 重试等待时间的计算公式与参数（基准值、乘数、上限）。
- 参数归属：放策略注册表还是全局配置。
- 服务端 `Retry-After` 与本地计算结果的取舍。
- 重试次数上限与延迟计算的配套关系。

### 非讨论范围

- 哪些错误来源归入 `retry` / `backoff_retry`（已由 [LLM 错误处理分类策略](.\2026-09-09-LLM错误处理分类策略.md) 决定，属策略注册表的判定职责）。
- `request/error` 事件的 payload 结构与 waterfall 订阅机制。
- `llm/retry` 记录的落盘格式细节。

### 模糊信息的明确定义

- **基准值 base**：第 1 次重试的等待时长，即用户所说的"基准值"。
- **乘数 multiplier**：每次重试等待时长相对上一次的放大倍数，通常取 2。
- **上限 cap**：等待时长的封顶值，防止重试间隔无限拉长。
- **retry_after**：服务端在限流响应头 `Retry-After` 中建议的重试等待秒数。

### 问题深度

涉及恢复策略的参数化与易变信息放置方式，属于长期可维护性决策，与 2026-09-09 ADR 的"策略与类型解耦"一脉相承。

## 现状

- [LLMRerty](..\..\src\myagent\agent\llm\llm_retry.py) 策略注册表已按错误类型返回 `decision`（`retry` / `backoff_retry` / `dont_retry`），但不携带任何延迟参数。
- [loop.step](..\..\src\myagent\agent\core\agent\loop.py) 已单点捕获 `LLMCallError`，并在 `finally` 中触发 `request/error` 拿到 `decision`，但**只打日志，未执行等待、未做重试计数**。
- [retry_delay](..\..\src\myagent\agent\core\agent\loop.py) 为空方法，是本次要落地的计算入口。
- [AgentConfig.max_retry_count](..\..\src\myagent\agent\core\agent\types.py) 已定义但未使用，是重试次数上限的现成承载。
- [Session.llm_retry_count(turn)](..\..\src\myagent\agent\core\session\session.py) 与 [LLMRetryData](..\..\src\myagent\agent\core\session\types.py) 已备好重试记录通道。
- provider 已从响应头解析 `Retry-After` 存入 `LLMCallError.details["retry_after"]`，见 [openai_provider._retry_after](..\..\src\myagent\agent\llm\openai_provider.py)，但尚无消费方。

## 决策前提

- 前提 1（用户决策）：重试延迟是**同一套算法、不同基准值**——`retry` 与 `backoff_retry` 不各写一套逻辑，差异只在基准值。
- 前提 2（用户决策）：退避形态取**指数 + 上限**，不引入抖动（保持可预测、可测试）。
- 前提 3（用户决策）：base / cap / 乘数等参数放**策略注册表 `LLMRerty`**，不放全局配置（延续 2026-09-09 ADR「策略易变、集中放独立注册表」）。
- 前提 4（用户决策）：服务端返回 `Retry-After` 时**优先采用**。
- 前提 5（现状约束）：重试次数上限已有承载（`AgentConfig.max_retry_count`）。
- 前提 6（用户约束）：本次先定设计再实现，设计以公式、参数归属、取舍规则为主，具体数值为可调初值。

## 可选方案

### 方案 A：统一退避公式 + 参数放策略注册表（选定）

所有可重试决策共用一条公式，第 n 次重试（n 从 1 开始）：

```
delay(n) = min(base * multiplier^(n-1), cap)
```

`retry` 与 `backoff_retry` 只是两组参数档位：

| decision | base | multiplier | cap | 语义 |
| -------- | ---- | ---------- | --- | ---- |
| `retry` | 0 | 2 | 0 | 立即重试（0, 0, 0, …） |
| `backoff_retry` | 1.0s | 2 | 30s | 1s → 2s → 4s → 8s → 16s → 30s（封顶后恒定） |

有服务端建议时：`delay = max(公式值, retry_after)`。

**优势**

- 一套公式两处参数，新增档位（如更激进/更保守的退避）只加一行参数，不改算法。
- 参数与"哪个错误用哪个档位"同处策略注册表，改策略只看一个文件（呼应前提 3）。
- `retry` 基准值取 0 时公式自然退化为"立即重试"，无需特判分支。

**劣势**

- 策略注册表需要从"只返回 decision"扩展为"返回 decision + 该档位参数"，决策返回值结构变复杂。

### 方案 B：retry 与 backoff_retry 各写独立延迟逻辑

`retry` 直接 `sleep(0)`，`backoff_retry` 单独实现指数退避。

**优势**：每个分支自解释，读代码直观。

**劣势**：违反前提 1；两条逻辑重复维护，新增档位要改多处，且"两套逻辑其实同源"的事实被代码掩盖。

### 方案 C：参数放全局 AgentConfig

公式在 loop，base / cap / 乘数作为全局配置放 `AgentConfig`。

**优势**：配置集中一处，调参不用碰策略判定代码。

**劣势**：把"同一策略的参数"与"策略判定"拆到两个文件——想调整某个策略的退避行为要看两处，且不同档位将共享同一组 base/cap，无法表达 `retry=0` 与 `backoff=1s` 的差异（除非在配置里再按 decision 分字段，等于把注册表搬到配置里）。违反前提 3。

## 决策逻辑

| 前提条件 | 对应方案 | 备注 |
| -------- | -------- | ---- |
| 前提 1 + 2 + 3 成立（当前状态） | 方案 A | 当前选择 |
| 需要"每个档位独立可读、不介意重复" | 方案 B | 备选触发条件 |
| 需要统一全局调参、且接受档位参数合并 | 方案 C | 备选触发条件 |

## 最终决策

当前成立的前提：前提 1、2、3、4、5、6。

因此选择 **方案 A**：LLM 重试等待时间统一走 `delay(n) = min(base * multiplier^(n-1), cap)`；`retry` 与 `backoff_retry` 只是 base 等参数不同的两个档位，参数与档位定义同放策略注册表 `LLMRerty`；错误带 `retry_after` 时取 `max(公式值, retry_after)`；重试次数上限沿用 `AgentConfig.max_retry_count`。

前提失效时的切换路径：见决策逻辑表。

## 决策原因

- 原因 1：`retry` 与 `backoff_retry` 本质是同一种恢复动作（等待后重试），差异只在等待时长（前提 1），用一条公式两组参数表达最贴合语义，避免两套同源逻辑。
- 原因 2：退避参数属于**易变信息**（需按线上表现调参），与"哪个错误走哪个档位"同属策略层；放策略注册表后，调整退避行为只需改一个文件（前提 3，延续 2026-09-09 ADR）。
- 原因 3：上限封顶避免长重试等待到不可接受（前提 2）；不加抖动换取可预测、可测试，抖动待有实证需要时再叠加（见决策逻辑防御性调整行）。
- 原因 4：`Retry-After` 是服务端对"多久后可用"的直接判断，比本地猜测更准；取两者较大值既尊重服务端又不低于本地退避下限（前提 4）。

## 后续影响

- `loop.step` 需补齐：拿到 `decision` 后，按决策计算延迟并等待、写一条 `llm/retry` 记录、判断是否达到 `max_retry_count`（达到则不再重试，走终止路径）。当前这两步均缺失。
- `retry_delay` 需要能读到错误本身（为取 `details["retry_after"]`），入参需携带错误或已提取的 retry_after；非 `LLMCallError`（如 `TimeoutError`）无 `details`，需容错。
- 第 n 次重试的 n 取自 `Session.llm_retry_count(turn) + 1`，依赖每次重试都写 `llm/retry` 记录。
- `LLMRetryData` 当前未继承 `SessionData` 且非 dataclass，落盘前需对齐（否则 `to_record_dict`/`asdict` 不可用）。
- 退避参数初值（`retry` base=0；`backoff_retry` base=1.0s、multiplier=2、cap=30s）为可调初值，依据线上重试成功率与耗时再修订。
- 本 ADR 只定公式、参数归属与取舍规则；重试终止/降级的具体路径、抖动引入与否，待相应实证后独立决策。
