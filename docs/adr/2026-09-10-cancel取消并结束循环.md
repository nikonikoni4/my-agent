# cancel 取消并结束循环

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿：cancel 与 stop 的语义分离（cancel 不打断循环 + stop 停止） |
| 2.0 | 决策反转：cancel 恢复"取消并结束循环"的原生语义，删除 stop |

## 问题界定

### 问题简述

loop 原先只有一个 `cancel()`，直接 `self._task.cancel()`。但 turn/step 内部已有自己的取消收口（step 捕获取消、记 interrupted 后结束本轮；turn 汇总为 interrupted），于是**同一个 `cancel()` 的后果由"取消落在哪个挂起点"决定**：

- 落在模型调用 / 工具执行（step 的 try 内）→ step 消化掉取消，`_loop` 完全看不到异常，循环继续；
- 落在空闲 `await self._wakeup.wait()` → `_loop` 无处理，整个循环终止；
- 落在退避 `asyncio.sleep`（step 的 finally 内）→ 异常从 finally 抛出、穿过 step，此时内层 finally 已用陈旧值写过 `step/end`，与 `turn/end` 的 interrupted 打架。

进一步追问暴露出更本质的冲突：**只要取消被内层吞掉（循环不被打断），任何"在等 loop task 结束"的外部机制都会永久挂起**——`asyncio.run()` 收尾的 `_cancel_all_tasks` + `gather`、`asyncio.wait_for` 的超时、测试 teardown、SIGINT 转发，都依赖被取消的协程真正结束。而 Python 自 3.8 起把 `CancelledError` 从 `Exception` 提升为 `BaseException` 子类，动机之一正是阻止健壮代码的通用 `except Exception` 兜底意外吸收取消——**"吞掉取消"本身就是与 asyncio 设计契约相悖的做法**，不是可以自由选择的实现细节。

### 讨论范围

- `cancel()` 的语义边界：是否结束循环。
- 取消异常在 step / turn / `_loop` 三层的传播与收口位置。
- 循环结束后的恢复路径（由谁负责重启）。

### 非讨论范围

- turn/step 把取消收口为 `interrupted` 的既有约定（本次沿用，只额外要求收口后原样上抛）。
- 退避等待期间被取消导致 `step/end` 落陈旧值的修正（独立问题）。
- inbox 的数据结构与优先级规则（`next_step` 先于 `next_turn`）。

### 模糊信息的明确定义

- **取消（cancel）**：向在途协程投递 `CancelledError` 的请求。它只是"登记一个请求"，真正投递的时机由事件循环决定，调用方不让出控制权就一直不投递。
- **打断循环**：使 `_loop` 协程终止，agent 不再消费后续消息。
- **在途任务**：正被 `_loop` await 的那一次 turn。
- **排队任务**：inbox 中尚未被消费的消息。

### 问题深度

架构原则问题：一是让组件的取消语义与承载它的运行时（asyncio）契约对齐；二是确定"取消异常在哪一层收口"——传播到最外层后由 `_loop` 消化，而不是被内层静默吞掉。

## 现状（决策时）

- `_task` 已是"整个 loop 一个 task"，`start()` 注册 `_on_loop_done` 取回未归一化异常。
- step / turn 已有各自的 `except asyncio.CancelledError` 收口（记 interrupted），但当时选择不上抛。
- `_loop` 的挂起点：空闲 `await self._wakeup.wait()`；在途 `await self.turn(...)`。
- 尚无外部消费者：只有测试调用 `start()` / `cancel()`。

## 决策前提

- 前提 1（机制事实，对话中实测确认）：`CancelledError` 只落在任务当时的挂起点，调用方不让出控制权就不会投递；而 loop 有多个挂起点，且 step 会消化落在自己 try 内的取消。因此"循环是否存活"取决于取消落点，是竞态。
- 前提 2（语言设计事实）：`CancelledError` 自 3.8 起继承 `BaseException`，动机之一是防止 `except Exception` 兜底吞掉取消。故"吞掉取消"与运行时契约冲突，不能作为稳定设计的基础。
- 前提 3（机制事实，对话中实测确认）：只要有机制在等 loop task 结束（`asyncio.run()` 收尾、`wait_for` 超时、`gather`、SIGINT、测试 teardown），取消被吞掉就会让其永久挂起；与调用方是否 `await` 该 task 无关。
- 前提 4（用户判断）：尽量与 asyncio 原设计对齐，避免可能的不兼容问题 → `cancel()` 应当具备"取消循环"的语义。
- 前提 5（用户判断）：取消的语义仍是"用户不再需要当前及之后排队的这批工作"，故 inbox 中排队的消息随之作废。
- 前提 6（用户判断）：`send()` 是唯一入口，循环停止后由 `send()` 按需重启；停下来的循环不占资源，反而节约资源。

## 可选方案

### 方案 A：cancel 恢复"取消并结束循环"语义（选定）

- `cancel()`：`self._task.cancel()` + 清空 inbox。
- 取消必须逐层传播：step 捕获后记本轮 interrupted 再 `raise`；turn 捕获后记 turn interrupted 再 `raise`；`_loop` 捕获后记一条 warning 并 `break`。
- 删除 `stop()`，不引入 `_stopping` 标志。
- `send()` 检测 `_task` 未在运行（`None` 或已 `done`）时自动 `start()` 重启。

**优势**

- 与 asyncio 原生语义对齐：外部等待方（`asyncio.run()` 收尾、`wait_for`、gather、SIGINT、测试 teardown）能正常结束，不会挂死。
- 取消只在 `_loop` 最外层消化，内层不吞；传播链清晰（step → turn → `_loop` 各自显式 `raise`/`break`）。
- 接口最小，无第二个公开方法；停止即休眠，`send()` 自动重启，循环停止期间不占资源。

**劣势**

- "只打断当前工作、保留循环与排队消息"不再是一等操作；`cancel()` 必然结束循环。
- `send()` 需承担重启职责（每次入口都要判存活）。

### 方案 B：cancel 不打断循环 + 新增 stop（v1.0 曾选定，本轮推翻）

- `cancel()`：取消在途 turn + 清空 inbox 但不上抛；`stop()`：先置 `_stopping` 标志再 cancel。

**优势**

- 两个意图各有明确手段：cancel = 放弃当前这批工作，stop = 结束组件。
- cancel 之后无需重新 `start()` 即可继续接消息。

**劣势（推翻原因）**

- 依赖内层"有意吞掉取消"，与 `CancelledError` 提升为 `BaseException` 的语言动机相悖（前提 2）。
- 任何绕过 `stop()` 的外部取消都会被循环吞掉，使等待方永久挂起（前提 3）——不兼容问题正是用户要规避的（前提 4）。
- 需要第二个公开方法与停止标志，复杂度更高。

### 方案 C：cancel 只打断当前轮，用 per-turn task 承载

`_task` 用于结束 loop，另为在途 turn 单独建 task 供 cancel 打断。

**优势**

- cancel 与循环生命周期落在不同 task 上，天然互不干扰，也不需要标志。

**劣势**

- 回到"每轮 turn 各建 task"的结构，`_task` 之外多一份在途句柄要维护。
- 在途 turn 的 task 由谁持有、何时释放需要额外规则，取消语义仍然分散在两层。

## 决策逻辑

| 前提条件 | 对应方案 | 备注 |
|----------|----------|------|
| 前提 1—6 成立 | 方案 A（cancel 取消并结束循环 + send 重启） | 当前选择 |
| 若未来需要"取消当前工作但保留循环与排队消息" | 需另设独立手段（如方案 C 的 per-turn task），不能复用 `cancel()` | 未预设 |
| 若未来 `cancel()` 之外还需"生命周期销毁"语义 | 另设 `stop()`/`close()` | 未预设 |

关于推翻条件：v1.0 曾声明"不预设推翻条件"，随后仍被前提 2、3（吞取消与 asyncio 契约冲突）推翻。**后续 agent 注意**：判断语义边界是否稳定时，须把"与承载运行时的契约是否一致"纳入，而不能只看局部使用路径成本（v1.0 就是被"cancel 后不用再 start"这一使用成本说服的）。本次仍不预设具体推翻条件，但已把上述复核维度显式记录。

## 演进历史

| 版本 | 方案 | 解决的问题 | 引入的新问题 |
| ---- | ---- | ---------- | ------------ |

## 最终决策

当前成立的前提：前提 1—6。

- **`cancel()`**：取消当前在途 turn、作废 inbox 中排队的 turn/step 消息，**并结束循环**（`self._task.cancel()`）。
- **取消异常的传播与收口**：step 记本轮 `interrupted` 后 `raise` → turn 记 `interrupted` 后 `raise` → `_loop` 捕获后记一条 warning 并 `break`；取消在 `_loop` 最外层被消化，任务以**正常结束**（非 cancelled）收场。
- **删除 `stop()`**，不引入 `_stopping` 标志。
- **`send()` 是唯一入口**：`_task` 为 `None` 或已 `done()` 时自动 `start()` 重启循环。

## 决策原因

- 原因 1（对应前提 1、2、3）：吞掉取消会让"等 task 结束"的外部机制永久挂起；`CancelledError` 提升为 `BaseException` 的动机之一就是防止兜底吸收取消。因此应让取消传播、由最外层消化，而不是在内层吞掉。
- 原因 2（对应前提 4）：与 asyncio 原设计对齐可避免可能的不兼容问题——这是用户推翻 v1.0 的直接理由。
- 原因 3（对应前提 5）：取消仍是"放弃这批工作"，inbox 中排队的消息一并作废。
- 原因 4（对应前提 6）：`send()` 作为唯一入口天然适合承担"按需重启"；循环停止期间不占资源。

## 后续影响

- **接口**：`ReActAgentLoop` 保留 `start()` / `send()` / `cancel()`，**无 `stop()`**；`cancel()` 语义 = 取消并结束循环。
- **实现**：`cancel()` 直接 `task.cancel()` + 清空 inbox；step / turn 的 `except CancelledError` 分支必须 `raise`（不能只 `break`）；`_loop` 用 `try` 包住整个 `while` 体，捕获 `CancelledError` 后 warning + `break`。
- **终态记录**：取消时 `step/end`、`turn/end` 照常收口为 `interrupted`（保持记录配对完整，取消在可观测链路上可查），turn/step 自身不打日志，由 `_loop` 记一条 warning。
- **测试**：`tests/agent/core/test_loop_paths.py` 以 E4（在途取消 → 结束循环、任务正常结束、无 error 日志）、E5（空闲态取消 → 结束循环、`send()` 可重启）、P5（取消记 interrupted 后原样上抛、task 处于 cancelled）锁定契约；测试收尾用 `cancel()`，见该文件的 `shutdown()`。
- **后续任务**：退避等待期间被取消导致 `step/end` 落陈旧值（独立问题，届时在 step 内层 finally 前判断是否正在被取消）。
