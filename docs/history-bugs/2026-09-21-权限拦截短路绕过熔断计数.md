# 权限拦截短路绕过熔断计数

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建初稿：权限拦截短路绕过熔断计数 |

## Bug简述

为工具配置了 `max_consecutive_failures`（含 `raise_on_break=True`）后，模型连续调用被权限护栏拒绝的工具，熔断始终不触发、`ToolConsecutiveFailureError` 不抛出。原因：护栏拒绝走 `ToolRegister.execute` 的权限拦截分支**短路返回**，该分支位于熔断计数路径之外，失败计数永远为 0。隐蔽在于配置本身完全合法（通过 `MIN_CONSECUTIVE_FAILURES` 下限校验），工具层与 loop 层均无报错，只有跑端到端测试才会发现。

## 复用场景

- **在 `execute` 执行链上新增"前置拦截/短路返回"分支时**（路径护栏、限流、功能开关、人在回路审批等）：只要产出 `is_error=True` 的 ToolResult，就必须显式决策"是否计入熔断计数"，不能默认短路即游离于计数之外。
- **`ToolErrorType` 新增错误分类时**：必须在错误分类矩阵（见 `docs/flows/2026-09-11-agent-loop错误处理.md` 链路 1）同步登记"是否计入熔断"，否则新分类会以"默认遗漏"的方式隐式获得语义——本 bug 的根源正是 `Permission_Denied` 未做该决策。
- 更一般的教训：**熔断计数入口与结果产出入口不是同一个函数时，新增结果产出路径必然绕过计数**。考虑把计数收敛到结果产出边界（如 execute 的统一返回点），而不是散落在 `_execute` 内部。

## 代码位置

- `src/myagent/agent/core/tool/register.py`
  - `execute` 权限拦截分支（修复前直接 `return ToolResult(...)`，不经过 `_execute`）
  - `_execute` 尾部熔断计数：`if result.is_error: self._on_failure(tool, result)`（被短路跳过）
  - `_on_failure`：计数累加、达阈值按 `raise_on_break` 抛 `ToolConsecutiveFailureError`
- `src/myagent/agent/core/agent/loop.py` `_tool_call`：先跑护栏 waterfall 取 vetoes，再以 `permission_passed=False` 调 `register.execute`
- 验证会话：`localData/sessions/D--desktop-软件开发-agent-lifeprismData-0159ea41/dff5fcf1-2018-4b81-a348-525742bf4cef.jsonl`

## 发生原因

`Permission_Denied` 是为工具护栏新增的错误分类。错误分类矩阵对 `TOOL_NOT_FOUND`（无熔断对象）、`BREAKER_INTERCEPT`（熔断后拦截）明确登记"不计入熔断"，但 `Permission_Denied` 新增时未做显式决策，当前实现等于默认"不计入"。

语义上熔断防的是"模型反复调用一个一直出错的工具"——模型侧写坏参数与工具侧执行失败都计入，而被护栏连续拒绝恰属此类（模型在反复发起注定失败的调用）。故应计入，未计入属遗漏而非设计。

## 最佳方案

权限拦截分支内对已注册工具补熔断计数（与 `_execute` 尾部同构）：

```python
if not permission_passed:
    # 没有通过权限检查
    result = ToolResult(
        f"status : error\n message : 工具调用({call.name})被权限护栏拦截。 deny_reason : {deny_reason}",
        error_type=ToolErrorType.Permission_Denied,
        duration_ms=int((time.perf_counter() - started) * 1000),
    )
    tool = self._tools[call.name]
    if result.is_error:
        self._on_failure(tool, result)
    else:
        self._consecutive_failures[tool.name] = 0
    return result
```

**修复后端到端验证**（2026-09-20 会话 dff5fcf1）：6 次并发 `read_file` 全部被路径护栏拒绝 → 第 5/6 次抛 `ToolConsecutiveFailureError`（step/end 记录 ExceptionGroup）→ `agent/error-handle` 决策 continue → step 2 的 request/header（reason=change）中 tools 列表 19→18，`read_file` 消失，schema_hide 生效，模型未再调用该工具。

## 遗留注意

1. **未注册工具 + 护栏拒绝会 KeyError**：上述方案用 `self._tools[call.name]` 直接下标访问；护栏按硬编码工具名表（`_PATH_PARAM_BY_TOOL`）拦截，不看注册表。若工具已 unregister 而模型仍调用，此处 KeyError 会经 TaskGroup 外溢使 turn 记 error。建议改 `.get()`，未注册跳过计数（同 TOOL_NOT_FOUND 语义）。
2. **一批并发调用可能抛多个熔断异常**：并发批次内第 5、6 次调用都越过阈值时，ExceptionGroup 含多个 `ToolConsecutiveFailureError` 子异常（loop 已能处理，仅日志观感问题）。若要求"每批最多抛一次"，可在 `_on_failure` 达阈值后先查 `tool.name in self._tripped` 再决定是否抛。
