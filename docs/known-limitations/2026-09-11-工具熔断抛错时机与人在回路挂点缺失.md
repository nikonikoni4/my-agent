# 工具熔断抛错早于 session 写入、且人在回路异步挂点缺失

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿 |

- 状态：`acknowledged`（当前由配置开关挡住，非 bug；待人在回路需求落地时改造）

## 1. 问题描述

`raise_on_break=True` 的工具在连续失败达到阈值时，由工具层内部直接抛出异常：

```
execute → _on_failure → raise ToolConsecutiveFailureError   # register.py
```

该异常在 `execute` 返回结果**之前**抛出，冒泡路径为：

```
ToolRegister.execute 抛出
  → asyncio.TaskGroup 包成 ExceptionGroup        # loop.step 的工具调用段
  → except ExceptionGroup 用 eg.split 取出         # loop.step
  → step_error = matched.exceptions[0]
  → finally → _handle_step_error → trigger(REQUEST_ERROR)
```

由此产生三个限制：

1. **会话不一致**：写 `tool/result` 的 for 循环位于 `async with TaskGroup` 之后。异常使 `TaskGroup.__aexit__` 直接抛 `ExceptionGroup`，该 for 循环不执行，于是本轮只留下一条带 `tool_calls` 的 `assistant/message`，**没有配对的 `tool/result`**（模型可见历史上是"请求了工具却没有结果"）。
2. **step 终态可能失真**：`_handle_step_error` 只在"重试耗尽"时把本轮记为 error；若订阅方返回非重试决策（`dont_retry` 或任意自定义值），它返回 `None`，`round_reason_type` 保持默认 `success`，`step/end` 被记成 success。唯有"无人认领 → 抛 `LLmError`"这条路径会把本轮记为 error。
3. **无法承载人在回路**：`request/error` 是**同步** waterfall（`callback(payload, _next)`），回调里不能 `await` 人；而 loop 只识别 `retry` / `backoff_retry` 两种决策，其它值一律解释为"不终止、继续 while 循环"，没有任何"暂停等人确认"的分支。即：外部订阅方现在只能**截获 + 出决策**，做不到**真正等待**。

> 说明：本文件是"当前系统受什么约束 + 为什么接受"的现状描述；具体改造形态见第 5 节的计划方向，不在本文件展开代码级细节。

## 2. 影响范围与严重程度

- **影响范围**：仅当某工具显式开启 `raise_on_break` 时，该工具熔断所中断的 turn。
- **严重程度**：**当前低**（默认配置下该路径不触发、外部无订阅方）；**接入人在回路后升为中**——届时会话不一致与终态失真会直接影响恢复决策与可观测性。
- **当前行为**：无订阅方时，`ToolConsecutiveFailureError` 经 `request/error` 得到 `None`，loop 抛 `LLmError`，整个 turn 记为 error（不会静默）。

## 3. 当前假设（系统依赖的脆弱前提）

1. **熔断必须先开配置才会触发**：`Tool.__init__` 的 `max_consecutive_failures` 默认 `None`，此时 `_on_failure` 直接 `return`，**根本不进入该路径**；`raise_on_break` 默认 `False`。只有显式配置了阈值与 `raise_on_break` 的工具才会走到"抛错"。
2. **外部尚无人依赖该路径**：人在回路/外部内容尚未开始，`request/error` 目前唯一订阅方是 `LLMRerty`，它不认领工具熔断错误、调用 `_next()` 交链尾，因此该路径的正确性尚无人消费。
3. **默认熔断走降级而非抛错**：`raise_on_break=False` 时，熔断表现为"给当次结果追加 hint + 后续从 schema 中隐藏（schema_hide）或入口驳回（execute_intercept）"，会话与终态不受影响。

## 4. 触发条件

- 某工具显式配置 `max_consecutive_failures`（阈值）**且** `raise_on_break=True`；
- 同一 turn 内该工具连续失败达到阈值；
- 或未来接入 `request/error` 的人在回路 / 可观测 / 评估订阅方，开始消费该路径。

## 5. 临时方案与计划改进

**临时方案**

- 保持 `raise_on_break` 默认关闭；需要熔断语义时先用 `schema_hide` / `execute_intercept` 的**降级**路径（不抛错，只回 hint 并隐藏/驳回），它不会造成上述会话与终态问题。
- 暂不依赖该路径做会话一致性，也不在其中承载人在回路。

**计划改进（方向已定，实现待人在回路需求启动）**

- **熔断不再在工具层抛**：`_on_failure` 统一为"标记熔断 + 给结果附加 hint + 正常返回 `ToolResult`"，由 `ToolResult` 上的标记承载"请求中断本 turn"。
- **由 loop 在写完会话后判定并抛出**：`step` 把每个 `tool/result` 都落盘之后，再检查结果上的熔断标记，在 `step` 的循环内将其作为 `step_error` 交出（仍汇入 `request/error`）。这样会话一致（`tool_calls` 与 `tool/result` 配对）且终态可正确记录。
- **为人在回路补异步挂点**：`request/error` 的订阅方只负责"识别 + 登记待人工 + 给出决策"，真正的"等待"由 loop 侧 `await` 一个由外部应答的 future 完成（或按超时降级为终止），避免在同步回调里阻塞事件循环。
